# Phase 60 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope Note (read first)

Per ROADMAP.md and 60-CONTEXT.md, this phase is **backend & sähköposti** — the full request-management dashboard (approve/reject list, sub-manager removal) is explicitly Phase 64 (ACCESS-04/ACCESS-07). This phase introduces exactly **three** user-facing surfaces, all minimal:

1. **"Copy invite link" button** (D-02/D-07) — owner-facing, added to `app/business/page.tsx`'s existing per-venue row.
2. **"Pyyntösi odottaa hyväksyntää" status banner** (D-06) — requester-facing, added to `app/business/page.tsx`, reusing the existing `StatusCard` pattern.
3. **Deep-link landing page** (`app/business/liity/page.tsx`, per RESEARCH.md A1) — reads `?paikka_id=X`, routes to signup-or-submit. This is intentionally bare: no design polish, no marketing copy — D-03 explicitly defers "polished signup-via-invite-link onboarding UX" to a future phase.

No new components, no new design tokens, no new color, no new typography. Every surface below is a **direct reuse** of `app/business/page.tsx`'s existing `StatusCard`/`VenueRow` glassmorphism patterns (read in full during research — see Design System Detected). The contract below documents which exact existing classes/patterns to reuse, so the executor does not improvise new visual language for a backend-focused phase.

## Interaction States (narrow, this phase only)

| Surface | State | Behavior |
|---------|-------|----------|
| "Kopioi kutsulinkki" button | Default | `buttonVariants()` outlined or filled small button, sits in the existing per-venue action row in `app/business/page.tsx` (alongside `esikatseluCta`/`muokkaaCta`) — only shown for venues where the current account's `claim_status === 'approved'` (only an approved owner can invite) |
| "Kopioi kutsulinkki" button | Clicked | `navigator.clipboard.writeText()` fires client-side (no API call, per RESEARCH.md); button label/icon briefly swaps to "Linkki kopioitu" confirmation for ~2s, then reverts |
| Pending banner | Shown | Appears in the same banner slot as `StatusCard`'s existing approved/rejected/pending variants — i.e., it is a new `StatusCard` branch keyed on "current account has a pending `business_access_requests` row", checked alongside the existing `hasApproved`/`allRejected` checks |
| Pending banner | Hidden | Not shown if no pending `business_access_requests` row exists for the current account, or after approval/rejection (banner is replaced by the existing approved/rejected `StatusCard` variants, which already handle those cases for the venue itself) |
| `/business/liity?paikka_id=X` | Valid link, not yet authenticated | Routes to existing signup flow (per RESEARCH.md A2/Pitfall 1 — exact mechanic left to planner per D-09a); no new signup screen design needed, reuse `/business/rekisteroidy` form styling unchanged |
| `/business/liity?paikka_id=X` | Valid link, authenticated, no pending request yet | Shows venue name (fetched via the submit-validation read) + "Lähetä pyyntö" button |
| `/business/liity?paikka_id=X` | Valid link, authenticated, pending request already exists (D-08) | Immediately shows the same pending-banner copy as the `/business` dashboard — no submit button, no error |
| `/business/liity?paikka_id=X` | Invalid `paikka_id` / no approved owner (D-10) | Shows the D-10 error copy above; no submit button rendered |
| `/business/liity?paikka_id=X` | Already belongs to a different company (D-09) | Shows the D-09 error copy above; no submit button rendered |

No animation requirements beyond the project's existing defaults (CLAUDE.md Animation Principles) — this phase introduces no new card grids, hover reveals, or view transitions. If the banner enters/exits, it should follow the existing crossfade-only rule (`opacity` in/out, no y-movement) already used elsewhere in `app/business/page.tsx`'s `AnimatePresence` usage, if any exists; otherwise no animation is required (static render is acceptable for a backend-focused phase).
