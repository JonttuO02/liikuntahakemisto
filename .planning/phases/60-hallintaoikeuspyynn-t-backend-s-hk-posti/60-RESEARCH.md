# Phase 60: Hallintaoikeuspyynnöt — backend & sähköposti - Research

**Researched:** 2026-06-25
**Domain:** Supabase Postgres RLS/concurrency-safe state machine + Resend transactional email, inside an existing Next.js Route Handler codebase
**Confidence:** HIGH

## Summary

This phase has no new external dependencies and no new architectural pattern to discover — it is a faithful structural replication of two patterns that already exist and are fully read in this codebase: `app/api/admin/approve/route.ts`'s concurrency-safe `UPDATE ... WHERE status='pending'` + `count:'exact'` approve flow, and `lib/email.ts`'s Resend send-function conventions (`sub()`/`esc()` helpers, non-critical try/catch at the call site). The only genuinely new artifact is the `business_access_requests` table and its RLS, which must compose with — not duplicate — the `current_company_id()` SECURITY DEFINER helper and column-privilege-grant pattern Phase 59 just established (and had to correct twice after discovering Supabase's pre-existing table-wide grants silently override column-level `REVOKE`).

The CONTEXT.md decisions (D-01 through D-10) fully resolve the "how does the requester find the venue" ambiguity in ACCESS-03's literal wording: there is no search UI in this phase. A deep link (`/business/liity?paikka_id=X`) generated by the owner (D-02 "Copy invite link" button) carries the `paikka_id`; the request-creation endpoint validates it against `business_paikka_links` (must have an approved row — D-10) and against the requester's own `business_accounts.company_id` (must be NULL — D-09) before inserting. The approval write (D-05) is a Route Handler using `supabaseAdmin`, mirroring `admin/approve` exactly: JWT verify → owner-role check → fetch row → guard non-pending → `UPDATE ... WHERE status='pending'` + `count:'exact'` → non-critical email in try/catch. Two new Resend-sending functions go into the existing `lib/email.ts` file, not a new module.

**Primary recommendation:** Build three new Route Handlers (`POST /api/business/access-request/submit`, `POST /api/business/access-request/approve`, `POST /api/business/access-request/reject`) that are near-line-for-line structural copies of `app/api/admin/approve/route.ts` and `app/api/business/reapply/route.ts`, add one migration creating `business_access_requests` with RLS modeled exactly on `business_paikka_links`'s existing policy shape, and add two functions to `lib/email.ts` following `sendAdminNotificationEmail`/`sendApprovalEmail`/`sendRejectionEmail`'s exact conventions.

### Pattern 1: Concurrency-safe approve/reject (replicate exactly)
**What:** Fetch row, guard `status === 'pending'`, then `UPDATE ... WHERE id = X AND status = 'pending'` with `{ count: 'exact' }`; if `count` is 0, another concurrent request already won — return 409.
**When to use:** Both the new `approve` and `reject` Route Handlers for `business_access_requests`.
**Example:**
```typescript
// Source: app/api/admin/approve/route.ts (this codebase, lines 43-59)
if (link.claim_status !== 'pending') {
  return NextResponse.json({ error: 'Application is not pending' }, { status: 409 })
}

const { error: updateLinkError, count } = await supabaseAdmin
  .from('business_paikka_links')
  .update({ claim_status: 'approved' }, { count: 'exact' })
  .eq('id', linkId)
  .eq('claim_status', 'pending')
if (updateLinkError) {
  return NextResponse.json({ error: 'Update failed', detail: updateLinkError.message }, { status: 500 })
}
if (!count) {
  return NextResponse.json({ error: 'Application already processed' }, { status: 409 })
}
```
Apply the identical shape to `business_access_requests`, swapping `claim_status` for `status` and `link_id` for the new request's `id`.

### Pattern 2: Non-critical email send (replicate exactly)
**What:** Email failures never roll back or fail the API response — wrap the `resend.emails.send` call (and its data lookups) in try/catch, `console.error` on failure, and still return `200`/`{ ok: true }`.
**When to use:** Both the "owner notified of new request" and "requester notified of decision" emails.
**Example:**
```typescript
// Source: app/api/admin/approve/route.ts (this codebase, lines 61-82)
try {
  const { data: authUser } = await supabaseAdmin.auth.admin.getUserById(link.business_account_id)
  // ...fetch related data...
  if (authUser?.user?.email && biz?.companies && paikka) {
    await sendApprovalEmail(authUser.user.email, { companyName: biz.companies.name, venueName: paikka.nimi })
  }
} catch (emailErr) {
  console.error('[admin/approve] Approval email failed (non-critical):', emailErr)
}
```

### Pattern 3: Idempotent insert for duplicate-submission (D-08 — new pattern, not yet in codebase)
**What:** D-08 requires the second submit to return the existing pending row, not error. The existing codebase patterns (`admin/approve`, `reapply`) are all "find-then-error-if-missing" or "find-then-409-if-already-processed" — neither matches D-08's "find-then-return-existing" idempotency requirement. This IS new to the codebase and needs explicit design:
```sql
-- Migration: partial UNIQUE constraint enforces idempotency at the DB layer
ALTER TABLE business_access_requests
  ADD CONSTRAINT business_access_requests_pending_unique
  UNIQUE (requester_id, paikka_id) -- combined with a partial index, see below
```
```typescript
// Route handler pattern: attempt insert, on unique-violation (Postgres code 23505)
// re-fetch the existing pending row and return it instead of erroring.
const { data: inserted, error: insertError } = await supabaseAdmin
  .from('business_access_requests')
  .insert({ requester_id: user.id, paikka_id })
  .select()
  .single()

if (insertError?.code === '23505') {
  // Unique violation -- a pending request already exists. Idempotent: fetch and return it.
  const { data: existing } = await supabaseAdmin
    .from('business_access_requests')
    .select()
    .eq('requester_id', user.id)
    .eq('paikka_id', paikka_id)
    .eq('status', 'pending')
    .single()
  return NextResponse.json({ ok: true, request: existing })
}
if (insertError) {
  return NextResponse.json({ error: 'Insert failed', detail: insertError.message }, { status: 500 })
}
return NextResponse.json({ ok: true, request: inserted })
```
**Note for planner:** This is the one piece of genuinely new logic in this phase. Flag it for explicit test coverage (two near-simultaneous submits from the same requester/paikka_id pair must both succeed and return identical data).

### Anti-Patterns to Avoid
- **SELECT-then-UPDATE without a WHERE status guard:** Every prior concurrency bug in this codebase's history was prevented by including `status='pending'` (or `claim_status='pending'`) directly in the UPDATE's WHERE clause, not just in a preceding SELECT. Do not check status in a SELECT and then UPDATE unconditionally — that's a TOCTOU race.
- **Column-level REVOKE without first REVOKE-ing the table-wide grant:** Phase 59 discovered (twice — `20260625000001` and `20260625000002`) that Supabase's pre-existing table-wide `GRANT UPDATE ... TO authenticated` silently overrides any column-specific `REVOKE UPDATE (col) ... FROM authenticated`. Any new column lockdown on `business_access_requests` MUST use `REVOKE UPDATE ON business_access_requests FROM authenticated` (whole table) followed by an explicit `GRANT UPDATE (allow-list)`.
- **A new RLS UPDATE policy letting users write other users' `business_accounts` row:** D-05 explicitly states this is NOT added — the approval write happens exclusively via `supabaseAdmin` (service role, bypasses RLS). Do not add a "company members can update teammates" RLS policy as a shortcut.
- **Building a venue-name/address search UI:** D-01 explicitly rejects this. `ClaimSearchForm.tsx` / `app/api/business/create-paikka` are confirmed NOT reusable here (CLAIM-04 already removed search functionality).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Concurrency-safe state transitions | A custom locking mechanism, advisory locks, or SELECT FOR UPDATE | `UPDATE ... WHERE status='pending'` + `{ count: 'exact' }` | Already proven correct in this codebase across 3+ routes; Postgres's row-level atomicity makes the WHERE-guarded UPDATE inherently race-free without explicit locking |
| Email header injection prevention | Custom regex/sanitization | `sub()` helper already in `lib/email.ts` | Already battle-tested; reuse, don't reimplement |
| XSS prevention in email HTML | Custom escaping | `esc()` helper already in `lib/email.ts` | Same file, same reasoning |
| Multi-tenant access control | A permissions library (CASL/Oso/Cerbos) | Plain Postgres RLS + `current_company_id()` | Explicit STATE.md decision: "avoid CASL/Oso/Cerbos/Clerk/WorkOS" — the access model (single owner approves, RLS denies until approved) is simple enough that a library would be net-negative complexity |

**Key insight:** Every piece of "hard" logic in this phase (concurrency, email safety, multi-tenant RLS) already has a correct, tested implementation elsewhere in this exact codebase. The research task is locating and replicating those patterns precisely, not inventing new ones — except for D-08's idempotent-insert pattern, which is genuinely new (see Pattern 3 above) and should get the most scrutiny during review.

## Schema Design: `business_access_requests`

### Confirmed current schema this phase composes with

**`business_accounts`** (after Phase 59, per `20260605000000_business_accounts.sql` + `20260625000000_companies_role_rls.sql` + `20260625000002_tighten_business_accounts_grant.sql`):
```
user_id          UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE
approval_status  TEXT NOT NULL DEFAULT 'pending' CHECK (approval_status IN ('pending','approved','rejected'))
created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
company_id       BIGINT NOT NULL REFERENCES companies(id)        -- added Phase 59
role             TEXT NOT NULL CHECK (role IN ('owner','member')) -- added Phase 59
-- company_name DROPPED in Phase 59 (replaced by companies.name via company_id FK)
-- contact_phone added 20260615000000 (not shown above, irrelevant to this phase)
```
RLS: "Business reads own account" (SELECT), "Business inserts own account" (INSERT), "Business updates own account" (UPDATE) — all `auth.uid() = user_id`. Column grant: only `contact_phone` is UPDATE-able by `authenticated` (per `20260625000002`); `role`/`company_id` writes are blocked at the grant level for `authenticated`, meaning **only `supabaseAdmin` (service role) can write `role`/`company_id`** — exactly what D-05's approval Route Handler requires, no new RLS/grant change needed for the approval write itself.

**`business_paikka_links`** (after Phase 59, per `20260605000000_business_accounts.sql` + `20260625000000_companies_role_rls.sql` + `20260625000001_fix_column_privilege_escalation.sql`):
```
id                  BIGSERIAL PRIMARY KEY
business_account_id UUID NOT NULL REFERENCES business_accounts(user_id) ON DELETE CASCADE
paikka_id           BIGINT NOT NULL REFERENCES liikuntapaikat(id) ON DELETE CASCADE
claim_status        TEXT NOT NULL DEFAULT 'pending' CHECK (claim_status IN ('pending','approved','rejected'))
link_type           TEXT NOT NULL CHECK (link_type IN ('claim','created'))
created_at          TIMESTAMPTZ NOT NULL DEFAULT now()
rejection_reason     TEXT                              -- added later, exact migration not re-verified this phase but confirmed present (used in app/business/page.tsx, reapply route)
submitted_at         TIMESTAMPTZ                        -- added 20260624120000_business_paikka_links_submitted_at.sql
updated_at           TIMESTAMPTZ                        -- present per 20260625000001's grant allow-list
UNIQUE (business_account_id, paikka_id)                 -- widened from UNIQUE(paikka_id) in Phase 59
```
RLS: SELECT is self-scoped to `business_account_id = auth.uid()` (`business_paikka_links_select_own`, rewritten in Phase 59, explicitly NOT widened to company-wide per D-14). INSERT/UPDATE policies unchanged (`auth.uid() = business_account_id`). Column grant allow-list (per `20260625000001`): `id, business_account_id, paikka_id, link_type, created_at, rejection_reason, updated_at, submitted_at` — note `claim_status` is **excluded** from the `authenticated` UPDATE grant (closes the self-approval hole WR-01 fixed). This means **only `supabaseAdmin` can write `claim_status`** — confirms D-05's approval write (which sets `claim_status='approved'` on a new `business_paikka_links` row for the requester) must go through `supabaseAdmin`, consistent with using `INSERT` (not `UPDATE`) for the requester's new row, which the INSERT policy (`auth.uid() = business_account_id`) would actually block anyway since the inserting actor is the owner approving on behalf of the requester, not the requester themselves — **this INSERT MUST happen via `supabaseAdmin`** (bypasses RLS entirely), matching D-05's explicit text.

**Existing "approved owner" lookup for D-10's validation:** A venue has a "current approved owner" if there exists a `business_paikka_links` row with `paikka_id = X AND claim_status = 'approved'`. This is the exact same predicate `StatusCard`/`VenueRow` in `app/business/page.tsx` already uses to render the green "approved" badge. D-10's submission-time guard is:
```sql
SELECT 1 FROM business_paikka_links WHERE paikka_id = $1 AND claim_status = 'approved'
```
If this returns zero rows, OR `paikka_id` is malformed (`NaN`/missing), reject the submission with a friendly Finnish error — no `business_access_requests` row is created (matches D-10 exactly).

### Proposed new table DDL

```sql
-- supabase/migrations/20260626000000_business_access_requests.sql
-- Phase 60 ACCESS-03/05/06: business_access_requests table + RLS + grants.
--
-- Analog sources:
--   supabase/migrations/20260605000000_business_accounts.sql
--     -- table/RLS triple structure (SELECT/INSERT/UPDATE policies, auth.uid() = owner-column)
--   supabase/migrations/20260625000000_companies_role_rls.sql
--     -- SECURITY DEFINER helper composition style, REVOKE/GRANT column-privilege pattern
--   supabase/migrations/20260625000001_fix_column_privilege_escalation.sql
--   supabase/migrations/20260625000002_tighten_business_accounts_grant.sql
--     -- CRITICAL: table-wide REVOKE UPDATE before column allow-list GRANT --
--        a column-only REVOKE does NOT narrow Supabase's default table-wide
--        GRANT. Any status/decision column lockdown here MUST follow this
--        two-step shape, not a column-only REVOKE.
--
-- Decision log (.planning/phases/60-hallintaoikeuspyynn-t-backend-s-hk-posti/60-CONTEXT.md):
--   D-08: partial UNIQUE on (requester_id, paikka_id) WHERE status='pending' --
--         enforces idempotent duplicate-submission handling at the DB layer.
--   D-09/D-10: validated by the submit Route Handler BEFORE insert, not by a
--         DB constraint -- these are business-logic guards, not data invariants
--         (a company_id can legitimately change in the future; "no approved
--         owner yet" is a transient state, not an invariant).

BEGIN;

CREATE TABLE IF NOT EXISTS business_access_requests (
  id               BIGSERIAL PRIMARY KEY,
  requester_id     UUID NOT NULL REFERENCES business_accounts(user_id) ON DELETE CASCADE,
  paikka_id        BIGINT NOT NULL REFERENCES liikuntapaikat(id) ON DELETE CASCADE,
  status           TEXT NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending', 'approved', 'rejected')),
  rejection_reason TEXT,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- D-08: partial UNIQUE -- only ONE pending request per (requester, venue) pair.
-- A requester CAN have multiple historical rejected/approved rows for the same
-- venue (e.g. rejected then re-submits) -- only 'pending' is uniqueness-guarded.
CREATE UNIQUE INDEX business_access_requests_pending_unique
  ON business_access_requests (requester_id, paikka_id)
  WHERE (status = 'pending');

ALTER TABLE business_access_requests ENABLE ROW LEVEL SECURITY;

-- Requester reads own requests (drives the D-06 "odottaa hyväksyntää" banner)
CREATE POLICY "Requester reads own access requests"
  ON business_access_requests FOR SELECT
  USING (auth.uid() = requester_id);

-- Owner reads requests targeting venues their company owns (for future Phase
-- 64 dashboard -- not used by any UI in THIS phase, but needed so the owner's
-- session can at minimum verify a request exists when manually approving via
-- the approve Route Handler's authorization check, OR simply rely on
-- supabaseAdmin for that read -- planner's choice; see Open Questions).
CREATE POLICY "Owner reads requests for owned venues"
  ON business_access_requests FOR SELECT
  USING (
    EXISTS (
      SELECT 1 FROM business_paikka_links bpl
      JOIN business_accounts ba ON ba.user_id = bpl.business_account_id
      WHERE bpl.paikka_id = business_access_requests.paikka_id
        AND bpl.claim_status = 'approved'
        AND ba.company_id = current_company_id()
        AND ba.role = 'owner'
    )
  );

-- Requester inserts own request (the submit Route Handler also runs the D-09/
-- D-10 business-logic guards BEFORE this INSERT executes; RLS WITH CHECK only
-- enforces identity, not the business rules, matching the codebase's existing
-- division of labor between RLS and Route Handler validation).
CREATE POLICY "Requester inserts own access request"
  ON business_access_requests FOR INSERT
  WITH CHECK (auth.uid() = requester_id);

-- NO client-writable UPDATE policy. status/rejection_reason transitions
-- (approve/reject) happen EXCLUSIVELY via supabaseAdmin in the approve/reject
-- Route Handlers (D-05's "no new RLS UPDATE policy ... service role"). This
-- mirrors business_paikka_links' claim_status lockdown (20260625000001) --
-- there, an UPDATE policy exists but the specific column is grant-revoked;
-- here, simplest correct option is no UPDATE policy at all for `authenticated`,
-- since no legitimate authenticated-client write path to this column exists.

COMMIT;
```

**Why no UPDATE RLS policy at all (vs. revoke-then-grant on a policy):** Unlike `business_accounts`/`business_paikka_links`, which had a pre-existing UPDATE policy serving legitimate non-status columns (`contact_phone`, `rejection_reason` set by the *business itself* on reapply), `business_access_requests` has **no legitimate authenticated-client UPDATE path at all** — every write to `status`/`rejection_reason` originates from the owner approving/rejecting someone else's row, which `supabaseAdmin` always bypasses RLS for. Omitting the UPDATE policy entirely is simpler and more defensive than creating one and then column-revoking it (avoids repeating Phase 59's REVOKE-doesn't-narrow-table-grant pitfall by construction).

## RLS Enforcement for Success Criterion 3 (pre-approval access block)

Success criterion 3 requires: "pyytäjä ei saa pääsyä paikan hallintaan ennen hyväksyntää — pääsy on estetty RLS-tasolla, ei vain UI:ssa." This is enforced by composition of EXISTING RLS, not new RLS:

- `business_paikka_links`'s SELECT policy is self-scoped (`business_account_id = auth.uid()`). Before approval, the requester has NO row in `business_paikka_links` at all — so any client-side query for "venues I manage" naturally returns nothing for them. No new policy needed; absence of a row is the enforcement mechanism.
- The approval write (D-05) is the ONLY thing that creates the requester's `business_paikka_links` row, and it happens via `supabaseAdmin`. Until that INSERT happens, the requester structurally cannot see or write to the venue's management data through any RLS-governed table, because `business_paikka_links` is the join table gating all of `app/business/[id]/page.tsx`'s reads.
- **Verify during planning:** confirm `app/business/[id]/page.tsx` (the venue management page) actually checks/queries `business_paikka_links` for authorization rather than trusting `paikka_id` alone — CR-01 in STATE.md's Carry-Forward section flags "`app/business/[id]/page.tsx` reads venue data without ownership check (pre-existing since Phase 38)" as a known gap. **This pre-existing gap may partially undermine success criterion 3** if not addressed — flag for the planner to verify whether this CR-01 gap is in scope to fix as part of "RLS-level" enforcement, since a page-level missing check is not itself an RLS bypass but does mean unauthorized reads could already be possible through that specific page regardless of this phase's new table. Recommend the planner explicitly test: can a pending (non-approved) requester load `/business/[id]` for the venue they requested, before approval?

```
1. JWT verify (supabaseAdmin.auth.getUser) -> 401 if missing/invalid
2. Parse + validate paikka_id from body -> 400 if missing/NaN
3. D-09: SELECT business_accounts WHERE user_id = user.id
     -> if row.company_id IS NOT NULL -> 400 "already belongs to a company"
   (if no business_accounts row exists at all, this is the brand-new-signup
    case D-03 describes -- planner must decide: does account creation happen
    BEFORE this endpoint is called, or does this endpoint also handle account
    creation? CONTEXT.md's framing implies signup is a separate upstream step
    -- recommend keeping account creation in the existing /api/business/register
    flow and having THIS endpoint require an existing business_accounts row,
    i.e. signup-then-request, not signup-as-part-of-request.)
4. D-10: SELECT 1 FROM business_paikka_links WHERE paikka_id = X AND claim_status = 'approved'
     -> if no row -> 400 "invite link invalid, no current owner"
5. D-08: attempt INSERT, catch unique-violation (23505), return existing pending row on conflict
6. Non-critical email to owner (try/catch)
7. Return { ok: true, request: <row> }
```

**Open question for planner:** D-09's guard reads `company_id IS NOT NULL` to mean "already belongs to a company." But EVERY `business_accounts` row has `company_id NOT NULL` after Phase 59's migration (it's a required column, backfilled for all existing rows, and `/api/business/register` always creates a fresh company for every new signup). This means **every existing business account, including a freshly-registered one via the existing `/api/business/register` flow, already has a non-null `company_id`** — which would make D-09's guard always trigger for anyone who registered through the normal flow, defeating the deep-link flow entirely for that population. **This needs explicit resolution during planning, not assumed by research:** either (a) the deep-link flow must create the `business_accounts` row WITHOUT going through `/api/business/register`'s "create a new company" step (i.e., a parallel, company-less registration path used only for invite-link signups), or (b) D-09's check is actually about something more specific (e.g., "has an existing OWNER role in a DIFFERENT company than the one they're requesting access to") rather than a blanket NULL check. Recommend the planner re-confirm this exact semantic with the user/CONTEXT.md author before implementing, since the literal `company_id IS NOT NULL` reading is provably unworkable given Phase 59's schema.

## Common Pitfalls

### Pitfall 1: D-09's literal `company_id IS NOT NULL` check is unworkable as stated
**What goes wrong:** Every `business_accounts` row has a NOT NULL `company_id` after Phase 59 (see Open Question above) — implementing D-09 literally would block 100% of submissions.
**Why it happens:** D-09 was likely written assuming a "no company yet" state could exist, which Phase 59's schema doesn't actually allow.
**How to avoid:** Resolve during planning whether the invite-link signup flow creates a `business_accounts` row via a DIFFERENT path that doesn't auto-create a company, or reinterpret D-09 (e.g. "already a member of a DIFFERENT company than the venue's owning company" — comparing against the specific `company_id` derivable from the `paikka_id`'s approved `business_paikka_links` row's owner).
**Warning signs:** If the planner writes the guard as `company_id IS NOT NULL` and tests it against any account created via the existing `/api/business/register` flow, every submission will be rejected.

### Pitfall 2: Forgetting the table-wide REVOKE before any future column lockdown
**What goes wrong:** Adding `REVOKE UPDATE (status) ON business_access_requests FROM authenticated` alone does nothing, because Supabase grants table-wide `UPDATE` to `authenticated` by default on every new table.
**Why it happens:** This exact mistake was made twice in Phase 59 (`20260625000000` then corrected by `20260625000001`).
**How to avoid:** This phase's recommended DDL avoids the issue entirely by adding NO UPDATE RLS policy and NO column grant for `authenticated` on `business_access_requests` — all status transitions go through `supabaseAdmin`. If a future column needs locking down, always `REVOKE UPDATE ON table FROM authenticated` (whole table) then `GRANT UPDATE (allow-list)`.
**Warning signs:** A client-side `.update()` call against `business_access_requests` from a browser context that unexpectedly succeeds in changing `status`.

### Pitfall 3: D-05's "no INSERT policy needed" assumption for `business_paikka_links`
**What goes wrong:** The approval Route Handler needs to INSERT a new `business_paikka_links` row for the requester, but the existing INSERT policy requires `auth.uid() = business_account_id` — the approving owner's `auth.uid()` is NOT the requester's `user_id`, so a client-side insert (even by the owner) would fail RLS.
**Why it happens:** This insert is being done ON BEHALF OF the requester, not BY the requester.
**How to avoid:** This INSERT must happen via `supabaseAdmin` (service role bypasses RLS entirely) — exactly as D-05 states ("the `business_paikka_links` grant for the requested venue using the service role"). Confirmed correct in the architecture above; flagging because it's an easy place to accidentally try the wrong client.
**Warning signs:** RLS violation error (`new row violates row-level security policy`) when testing the approve endpoint.

### Pitfall 4: Race between D-10's validation and a concurrent rejection/un-approval of the venue's owner link
**What goes wrong:** Between the D-10 check (SELECT approved `business_paikka_links` row exists) and the actual INSERT into `business_access_requests`, the venue's owner link could theoretically be rejected/removed by another process. This is a low-probability TOCTOU window, not the primary concurrency concern of this phase (which is approve-vs-approve, covered by Pattern 1).
**Why it happens:** Standard check-then-act gap; D-10 doesn't specify a constraint-level guard, only an API-level guard.
**How to avoid:** Accept this as a known, low-risk gap (no requirement calls for a stricter guarantee here) — document it rather than over-engineer a FK-based solution. The `business_access_requests.paikka_id` FK to `liikuntapaikat` already prevents inserting against a deleted venue; the "has an approved owner" check is a business rule, not a referential-integrity one, and a brief race window here has no security impact (worst case: an access request exists for a venue that briefly had no approved link, which the future approve flow would just re-validate).
**Warning signs:** Not a planning blocker — note in plan but don't gate on it.

### Pitfall 5: Email sent to wrong recipient if multiple owners exist per company (future-proofing note)
**What goes wrong:** The "owner notified of new request" email needs to resolve which auth user's email to send to. Since this phase's model is "single päähallitsija (owner) per venue" (per PROJECT.md), there is exactly one `business_accounts` row with `role='owner'` whose `business_paikka_links` row for the target `paikka_id` has `claim_status='approved'`. This lookup is a join across `business_paikka_links` → `business_accounts` filtered by `role='owner'`.
**Why it happens:** Easy to accidentally query company-wide owners instead of venue-specific owner if multiple venues/owners exist within a company in the future.
**How to avoid:** Always scope the owner lookup by `paikka_id` (via `business_paikka_links.claim_status='approved'`), not just by `company_id` + `role='owner'` — a company could (in theory, post-Phase-64) have an owner who doesn't manage this specific venue if `business_paikka_links` becomes per-venue-scoped to non-owners too. For THIS phase's data shape (single owner, D-04's narrow venue-only grant), this distinction is moot today but the query should be written defensively.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Privilege escalation via spoofed `user.id` in request body | Tampering / Elevation of Privilege | Never trust `body.user_id`/`body.requester_id` — always use the JWT-verified `user.id` from `supabaseAdmin.auth.getUser(token)`, exactly as every existing Route Handler in this codebase does |
| Email header injection via unescaped subject interpolation | Tampering | Reuse `lib/email.ts`'s existing `sub()` helper (strips CR/LF) on every interpolated string in a new email subject |
| XSS via unescaped user data in email HTML body | Tampering | Reuse `lib/email.ts`'s existing `esc()` helper on every interpolated string in a new email HTML body (e.g. `rejection_reason`, requester/venue names) |
| TOCTOU double-approval race | Tampering / Denial of Service (resource exhaustion if it created duplicate grants) | `UPDATE ... WHERE status='pending'` + `{ count: 'exact' }` atomic guard, per Pattern 1 |
| RLS bypass via missing/incorrect policy on new table | Elevation of Privilege | `business_access_requests` ships with `ENABLE ROW LEVEL SECURITY` and explicit SELECT/INSERT policies only — no default-allow gaps; verify via Supabase dashboard policy list before considering the migration complete |
| Self-approval via client-writable status column | Elevation of Privilege | No UPDATE RLS policy + no `authenticated` UPDATE grant on `business_access_requests` at all — status changes ONLY via `supabaseAdmin` in the approve/reject Route Handlers, closing the exact class of bug that `claim_status`/`approval_status` self-elevation fixes addressed in `20260605000003`/`20260625000001` |
