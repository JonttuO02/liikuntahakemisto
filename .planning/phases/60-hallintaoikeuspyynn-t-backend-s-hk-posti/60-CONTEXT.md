# Phase 60: Hallintaoikeuspyynnöt — backend & sähköposti - Context

**Gathered:** 2026-06-25
**Status:** Ready for planning

<domain>
## Phase Boundary

A päähallitsija (owner) generates a shareable invite link for a specific venue they manage. A new employee opens that link, registers a new business account (or the link carries them through a signup step — full onboarding UX for that is deferred), and submits an access request tied to that venue's `paikka_id`. The owner gets a Resend email when the request arrives; approving or rejecting it (and the email back to the requester) is concurrency-safe, mirroring `admin/approve`. Approval grants the new member visibility into exactly the requested venue (not company-wide) and a minimal "odottaa hyväksyntää" status surfaces to the requester. The full dashboard UI for managing pending requests (ACCESS-04, sub-manager removal ACCESS-07) is explicitly Phase 64 — this phase only needs enough UI to make the link-generate → request → approve loop usable and testable.

</domain>

<decisions>
## Implementation Decisions

### Venue lookup / invite mechanism
- **D-01:** No search-by-name/address UI. The mechanism is a shared deep link (e.g. `/business/liity?paikka_id=X`) generated by the existing owner and shared manually (Slack/WhatsApp/in person) — not the literal "hakee paikan nimellä/osoitteella" search implied by ACCESS-03's wording. This was a deliberate trade against building search UI.
- **D-02:** The owner generates the link via a small "Copy invite link" button somewhere on `/business` (not manual URL construction) — minor UI addition, but removes guesswork/typos.
- **D-03:** Signing up happens via the link — i.e. a brand-new employee with no existing account opens the link, creates their account through that flow, and the access request is what attaches them to the inviting venue/company. Full onboarding UX polish for "signup via invite link" is explicitly deferred (see `<deferred>`); Phase 60 only needs the request-creation step to work end-to-end, not a polished signup screen.

### Post-approval access scope
- **D-04:** Approval grants the new member access to ONLY the specific venue they requested — not company-wide visibility on `business_paikka_links`. The company-wide RLS widening that Phase 59 deferred to "Phase 60/64" is NOT delivered in this phase either; it remains open for Phase 64 (or later) if/when it's actually needed.
- **D-05:** Approval write path: a Route Handler (mirroring `admin/approve`) verifies the approver's JWT and owner role via `supabaseAdmin`, then performs the `business_accounts.company_id`/`role` update AND the `business_paikka_links` grant for the requested venue using the service role (bypasses RLS) — concurrency-safe `UPDATE ... WHERE status = 'pending'` + `count: 'exact'`, same pattern as `admin/approve`. No new RLS UPDATE policy is added to let one user write another user's `business_accounts` row.

### UI surface in this phase
- **D-06:** Phase 60 ships a bare-minimum status page/banner (e.g. on `/business`, "Pyyntösi odottaa hyväksyntää") for the requester once they have a pending `business_access_requests` row — not zero UI, but explicitly NOT the Phase 64 dashboard redesign. No request-management list/approve-reject buttons here (ACCESS-04/07 is Phase 64).
- **D-07:** The owner-side "Copy invite link" button (D-02) is the only owner-facing UI this phase adds.

### Request table & edge cases
- **D-08:** Duplicate submission: `business_access_requests` has a partial UNIQUE constraint on `(requester_id, paikka_id) WHERE status = 'pending'`. A second submit attempt while one is already pending is idempotent — it returns the existing pending request rather than erroring (matches the "already has a draft" graceful pattern used elsewhere in onboarding, not the 409-style admin/approve pattern).
- **D-09:** If the requester (an existing `business_accounts` row) already has a `company_id` set and opens someone else's invite link, the request is blocked at submission time with a clear error. Switching companies is not a supported flow — one business_account belongs to exactly one company, no requirement asks for reassignment.
- **D-10:** If the invite link's `paikka_id` has no current approved owner (no matching `business_paikka_links` row), or the link is malformed, the API rejects at submission with a friendly Finnish error — no orphan pending request rows are created.

### Claude's Discretion
- Exact `business_access_requests` table columns beyond `requester_id`, `paikka_id`, `status`, timestamps, and the partial UNIQUE constraint (D-08) are left to planning/research.
- Exact wording/placement of the "Pyyntösi odottaa hyväksyntää" banner (D-06) and the "Copy invite link" button (D-02) within `/business` is left to planning — no specific layout was discussed.
- Whether the new-employee signup-via-link flow reuses the existing business registration form as-is or needs a thin wrapper is left to research — only the end-to-end request-creation outcome (D-03) is locked, not the exact signup screen.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `app/api/admin/approve/route.ts` — direct template for the new approve/reject Route Handlers (D-05).
- `lib/email.ts` — extend with new functions for access-request notification + decision emails; do not create a parallel email helper.
- `app/business/page.tsx` (~lines 1–40, `VenueLink`/`VenueLiikuntapaikka` types and venue-status rendering) — the bare-minimum status banner (D-06) slots into this existing page's rendering logic, which already handles per-venue status badges (`deriveVenueStatus`).

### Established Patterns
- Every Route Handler in this codebase verifies JWT via `supabaseAdmin.auth.getUser(token)` before any DB read — new access-request endpoints (submit/approve/reject) must do the same (CLAUDE.md constraint, also enforced in `admin/approve`).
- Concurrency-safe state transitions always use `UPDATE ... WHERE status = 'pending'` + `{ count: 'exact' }`, never a SELECT-then-UPDATE without the WHERE guard — confirmed pattern across `admin/approve` and Phase 59's RESEARCH.md note ("Replicate admin/approve route's concurrency pattern for peer approval — do not reinvent").
- All Supabase writes from Route Handlers use the service-role client (`supabaseAdmin`); anon-key writes are never relied on for privileged state changes (CLAUDE.md constraint).

### Integration Points
- `business_accounts.company_id`/`role` (Phase 59) is what the approval write (D-05) ultimately sets for the new member.
- `business_paikka_links` is what the approval write (D-05) grants for the single requested venue (D-04) — exact mechanic (new row vs. existing row mutation) is left to planning since `business_paikka_links` is currently one-row-per-(business_account_id, paikka_id) after Phase 59's composite UNIQUE.
- `ClaimSearchForm.tsx` / `app/api/business/create-paikka` — confirmed NOT reusable for this phase (CLAIM-04 already removed all search functionality from this codebase; D-01 deliberately avoids rebuilding it).

- The owner-side affordance is literally a "Copy invite link" button (D-02) — the user's own phrasing, not a Claude suggestion.
- The user's framing: "the common way to add new users for the same venue would be that also the signing up is done after opening the link... later we could make an onboarding for that scenario" — confirms the link-driven signup is the intended long-term UX, with this phase delivering the working mechanism (not the polished screen) and a richer signup-from-link onboarding explicitly left for later.
