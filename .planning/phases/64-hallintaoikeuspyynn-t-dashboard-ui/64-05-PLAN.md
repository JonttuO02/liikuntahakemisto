<objective>
Close the single UAT gap from Phase 64 Test 3: after approving a pending
access request in the team management popup, the newly-approved member does
not appear in the "Current team" list until the popup is closed and reopened.

Root cause (confirmed, .planning/debug/team-list-no-refresh-approve.md):
`handleApprove` in app/components/TeamManagementPopup.tsx updates only
`pendingRequests` state on success (removing the approved row) but never
appends the member to `teamMembers` state, which backs the "Current team"
section. `teamMembers` is repopulated only by the fetch effect that runs on
popup open, so the approved member is invisible until reopen.

Purpose: Restore the expected immediate-feedback UX for the approve flow
(ACCESS-04) — the mutation already succeeds server-side; only the client's
optimistic list update is incomplete.

Output: A pure, unit-tested mapper (`pendingRowToTeamMember`) that converts an
approved pending row into a team-member row, wired into `handleApprove` so the
approved member moves between the two lists in one render pass.
</objective>

    Create lib/teamManagement.ts as the single source of truth for the two row
    shapes and the approve-flow mapper:
    - Export `type PendingRequestRow = { id: number; requesterId: string; name: string; email: string | null }`.
    - Export `type TeamMemberRow = { userId: string; name: string; email: string | null; role: string | null; isSelf: boolean }`.
      These MUST be structurally identical to the two inline `type` declarations
      currently at the top of app/components/TeamManagementPopup.tsx.
    - Export `function pendingRowToTeamMember(row: PendingRequestRow): TeamMemberRow`
      returning { userId: row.requesterId, name: row.name, email: row.email, role: 'member', isSelf: false }.
      Keep it pure (no imports, no side effects), matching the lib/ helper convention
      seen in lib/onboardingUtils.ts.

    Create lib/teamManagement.test.ts using vitest (import { describe, it, expect } from 'vitest'),
    mirroring the structure of lib/onboardingUtils.test.ts. Cover both behavior cases above.

    Edit app/components/TeamManagementPopup.tsx:
    - Remove the two inline `type PendingRequestRow` and `type TeamMemberRow` declarations
      and import both types plus `pendingRowToTeamMember` from '@/lib/teamManagement'.
    - In `handleApprove`, inside the `if (res.ok)` branch ONLY (do not touch the 409 or else
      branches), before or alongside the existing setPendingRequests filter, look up the
      approved row from the current `pendingRequests` by id, then append it to teamMembers:
        const approved = pendingRequests.find(r => r.id === requestId)
        setPendingRequests(prev => prev.filter(r => r.id !== requestId))
        if (approved) {
          setTeamMembers(prev =>
            prev.some(m => m.userId === approved.requesterId)
              ? prev
              : [...prev, pendingRowToTeamMember(approved)]
          )
        }
        onChanged?.()
      The `prev.some(...)` guard prevents a duplicate row if the member is already present.
      This mirrors the optimistic-update pattern already used in handleConfirmRemove
      (which correctly mutates its own list on success). Leave handleReject and
      handleConfirmRemove unchanged.
