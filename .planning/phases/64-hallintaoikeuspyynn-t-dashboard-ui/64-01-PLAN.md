<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → list Route Handler | Untrusted caller-supplied `paikka_id` query param + bearer token cross here |
| Route Handler → auth.users / business tables | Service-role read that bypasses RLS to resolve other users' identity |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-64-01 | Information Disclosure | GET /api/business/access-request/list | high | mitigate | Venue-scoped owner authorization (approved `business_paikka_links` row for the specific `paikka_id` AND `business_accounts.role==='owner'`) before any identity read; a non-owner receives 403 with no body (Task 2 steps 3) |
| T-64-02 | Elevation of Privilege / IDOR | owner-auth probe | high | mitigate | Authorization is keyed on the caller's own `business_account_id` + the requested `paikka_id`; a caller cannot read another venue's roster by changing the query param unless they hold an approved owner link to it |
| T-64-03 | Spoofing | bearer token | high | mitigate | `supabaseAdmin.auth.getUser(token)` verifies the JWT server-side; `user.id` is never taken from the request body/query |
| T-64-04 | Information Disclosure | anon browser client | medium | mitigate | All cross-account reads happen via `supabaseAdmin` in the handler; RLS self-scoping on business tables stays intact and is never widened (D-09 chose service-role over new RLS) |
</threat_model>
