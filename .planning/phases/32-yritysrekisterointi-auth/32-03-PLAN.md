<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser form→supabase.auth.signUp | Client sends email+password to Supabase Auth directly |
| browser→POST /api/business/register | Client sends JWT (Authorization header) + company_name; Route Handler verifies JWT |
| AuthModal SIGNED_IN event→business_accounts | Client queries via anon key; RLS allows SELECT where auth.uid() = user_id |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-32-03-01 | Elevation of Privilege | /business/rekisteroidy → Route Handler | mitigate | JWT sent in Authorization header; Route Handler (Plan 02) verifies with supabaseAdmin.auth.getUser before using user.id — body.user_id ignored |
| T-32-03-02 | Spoofing | AuthModal business redirect check | accept | Query uses anon key with RLS (SELECT WHERE auth.uid() = user_id) — RLS prevents querying another user's business_accounts row; if no row → regular user flow |
| T-32-03-03 | Tampering | company_name input on registration page | mitigate | Client: HTML required attribute + trim before POST; Server (Plan 02): server-side trim + slice(0, 200) before INSERT |
| T-32-03-04 | Denial of Service | Repeated registration attempts (account enumeration) | accept | Supabase Auth handles rate limiting; error messages do not distinguish between "email taken" and "server error" at the auth layer (Supabase returns consistent error codes) |
| T-32-03-05 | Information Disclosure | Error messages on registration page | accept | mapBusinessError maps Supabase error strings to generic user-facing strings; no raw Supabase error details exposed in UI |
| T-32-03-SC | Tampering | npm/pip/cargo installs | accept | Phase 32 installs zero new packages — no slopcheck gate required |
</threat_model>
