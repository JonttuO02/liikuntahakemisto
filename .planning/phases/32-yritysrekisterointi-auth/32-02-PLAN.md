  <action>
    Create app/api/business/register/route.ts as a Next.js App Router Route Handler exporting a POST function.

    Security requirement (RESEARCH.md security gap): The route MUST verify the JWT from the Authorization header before accepting any user data. Use `supabaseAdmin.auth.getUser(token)` to verify — then use `user.id` from the verified result for the INSERT. Never use the client-supplied body.user_id for the INSERT.

    Implementation sequence:
    1. Extract Authorization header: `request.headers.get('Authorization')` — split on 'Bearer ' to get the token.
    2. Call `supabaseAdmin.auth.getUser(token ?? '')` — if error or no user, return NextResponse.json({ error: 'Unauthorized' }, { status: 401 }).
    3. Parse request body (in try/catch for invalid JSON): extract company_name from body.
    4. Validate company_name: must be a non-empty string after trim. If missing or empty, return { error: 'Missing fields' }, status 400.
    5. Sanitize company_name: `company_name.trim().slice(0, 200)`.
    6. Use `user.id` (from step 2, not body) as the user_id for the INSERT.
    7. Call `supabaseAdmin.from('business_accounts').insert({ user_id: user.id, company_name })`.
    8. If INSERT error: call `await supabaseAdmin.auth.admin.deleteUser(user.id)` (atomicity rollback per D-10), then return { error: 'business_accounts insert failed', detail: error.message }, status 500.
    9. On INSERT success: return NextResponse.json({ ok: true }).

    Imports:
    - `import { NextResponse } from 'next/server'`
    - `import { supabaseAdmin } from '@/lib/supabaseAdmin.server'`

    No other imports needed. Do NOT import createServerSupabase, cookies, or any client-side modules.

    The client (registration page) will send the JWT via the Authorization header as:
    `Authorization: Bearer <session.access_token>`

    The client sends company_name in the POST body. The client ALSO sends user_id in the body (per the original D-09 design) but the Route Handler IGNORES body.user_id and uses user.id from JWT verification instead — this prevents the elevation-of-privilege vulnerability identified in RESEARCH.md.
