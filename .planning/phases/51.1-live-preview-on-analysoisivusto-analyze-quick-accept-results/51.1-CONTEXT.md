# Phase 51.1: Live preview on AnalysoiSivusto analyze/quick-accept results screen - Context

**Gathered:** 2026-06-18
**Status:** Ready for planning

<domain>
## Phase Boundary

`app/business/onboarding/AnalysoiSivusto.tsx` — the pre-wizard "Analysoi sivustosi" screen where the AI website-analysis results land (logo/color/gallery pickers, scraped price/hours lists) and where the user can either continue into the wizard or quick-submit directly — currently renders no card preview at all. This phase adds the same live `CalloutCard`/`DiagonaalKortti` preview used throughout the wizard (Phase 51) to this screen's `preview` phase, so the user sees the actual venue card before quick-submitting or continuing.

This closes a scoping gap: Phase 50's summary flagged "missing live preview during the AnalysoiSivusto analyze step" as expected Phase 51 work; Phase 51's CONTEXT.md excluded `AnalysoiSivusto` with the reasoning "they happen before any previewable field exists yet" — true for `AnalysoiSivusto`'s `checking`/`url-input`/`analyzing`/`error`/`timeout` phases, but NOT true for its `preview` phase, where `brandingResult` is fully populated and previewable.

</domain>

<decisions>
## Implementation Decisions

### Scope: which fields are live vs static
- **D-01:** Only the fields the user can actually edit on this screen update the preview live: logo selection, background/accent color selection, gallery image selection. Pricing, opening hours, and contact info (puhelin/kuvaus/website) are NOT editable here today and stay exactly as `buildBrandingPreview` already derives them from the frozen `raw_analysis` snapshot — no new inline editors for those fields on this screen. This is a deliberate scope boundary (confirmed with user): adding price/hours/contact editing to this screen would be a separate, larger phase.

### Layout: reuse the wizard's exact split-view/toggle pattern
- **D-02:** User explicitly asked for "the same logic as in the onboarding" — i.e., replicate `WizardInner.tsx`'s exact desktop split-view (sticky `w-[360px]` right column above `lg:`) + mobile segmented toggle (`LivePreviewToggle`, `lg:hidden`) pattern verbatim, not a simpler "just append the card somewhere" placement. See `app/business/WizardInner.tsx` lines 250-341 for the exact JSX shape to mirror:
  ```
  <LivePreviewProvider ...>
    <div className="flex gap-6 items-start justify-center">
      <div className="w-full max-w-xl">
        {/* existing AnalysoiSivusto phase content */}
        <div className="lg:hidden"><LivePreviewToggle activeView={activeView} onChange={setActiveView} /></div>
        {activeView === 'preview' ? <div className="lg:hidden"><LivePreviewPane /></div> : <>{existing content}</>}
      </div>
      <div className="hidden lg:flex flex-col gap-4 w-[360px] flex-shrink-0 sticky top-6">
        <LivePreviewPane />
      </div>
    </div>
  </LivePreviewProvider>
  ```
- **D-03:** The split-view/toggle treatment applies ONLY to `AnalysoiSivusto`'s `preview` phase (where `brandingResult` exists and there's something to show). The earlier phases (`checking`, `url-input`, `analyzing`, `error`, `timeout`) keep their current single-column rendering unchanged — Phase 51's original "no previewable field exists yet" reasoning is correct for those sub-phases, just not for `preview`.

### Reused components — no new preview UI to build
- **D-04:** `LivePreviewPane` (`app/business/onboarding/LivePreviewPane.tsx`) and `LivePreviewToggle` are pure presentational components with no split/toggle logic baked in — they read `useLivePreview()` and render. Reuse both as-is, unmodified. No new preview component needed.

### Provider wiring — new prop threading required
- **D-05:** `AnalysoiSivusto` needs its own `LivePreviewProvider` instance scoped to its `preview` phase only (no continuity needed with the wizard's separate provider instance that mounts later — the wizard reads the already-persisted logo/color selections fresh from `business_branding` on its own mount, since `AnalysoiSivusto`'s pickers already autosave via `patchBranding`/PATCH `/api/business/branding`).
- **D-06:** `LivePreviewProvider` requires a full `PaikkaBase` (`nimi`, `laji`, `osoite`, `kaupunki`, `latitude`, `longitude`) — but `AnalysoiSivusto` currently receives only `paikkaId` as a prop (see `app/business/onboarding/page.tsx`'s `PrePhase` wrapper, lines 99-160) and has no `paikkaInfo` of its own. `StepPaikkaPrePhase` (the pre-phase rendered just before this one) already fetches partial info via `select('nimi, osoite, kaupunki')` (page.tsx line ~71) but only passes it to `StepPaikka`, not forward to `AnalysoiSivusto`. Required plumbing: extend that query to `select('nimi, laji, osoite, kaupunki, latitude, longitude')`, thread the full `PaikkaBase` through `OnboardingWizardPage`'s state into `PrePhase`/`AnalysoiSivusto` as a new prop, mirroring how `paikkaId` is already threaded via `onPaikkaIdResolved`.
- **D-07:** Seed the provider's `state.media_urls.logo` indirectly through `selectedLogoUrl` (already in `AnalysoiSivusto`'s local state) — the provider's `brandingData` branch already overlays `state.media_urls?.logo` as `buildBrandingPreview`'s 4th argument (see `lib/livePreview/LivePreviewContext.tsx` line ~141), so dispatching `SET_MEDIA` with the locally-selected logo on every `selectLogo()` call (and similarly for color picks, though colors flow through `brandingData.selected_background_color`/`selected_accent_color` directly, not through `state` — see Claude's Discretion below for exact wiring) keeps the preview in sync with picks made on this screen.

### Claude's Discretion
- Exact dispatch wiring for color picks: `brandColor`/`accentColor` in `LivePreviewContext.tsx` are derived from the `brandingData` prop directly (`brandingData?.selected_background_color` etc., lines 149-157), NOT from reducer `state` — so updating the preview's colors as the user picks on this screen likely means passing the LOCAL `bgColor`/`accentColor` state (not the original `brandingResult` prop) into `LivePreviewProvider`'s `brandingData` prop (e.g. spread `{ ...brandingResult, selected_background_color: bgColor, selected_accent_color: accentColor }`, the same merge `AnalysoiSivusto`'s existing `onConfirm` call already does at line 880) rather than adding a new reducer action. Pick whichever wiring is more consistent with the existing reducer's shape — full freedom here since this is a new integration point, not a fix to existing dispatch logic.
- Exact gallery-pick wiring: `selectedGallery` (local state) maps to `state.media_urls.photos` — dispatch `SET_MEDIA` with `photos: selectedGallery` alongside the logo on every `toggleGalleryImage()` call, or derive it inline when building the `brandingData` override object passed to the provider. Either approach is fine.
- Whether to update the existing `useDebouncedPreviewField` hook's usages or add a new one here — this screen has no free-text fields requiring debounce (logo/color/gallery are all discrete-selection, instant-update per D-05 from Phase 51's original CONTEXT.md), so no debounce hook is needed at all for this phase.
- Whether `PrePhase`'s `paikkaInfo` fetch extension (D-06) duplicates `StepPaikkaPrePhase`'s existing query inline in `page.tsx` or factors out a small shared fetch helper — either is fine; this codebase doesn't have a strong precedent either way for two adjacent components needing overlapping Supabase selects.

</decisions>
