### Code Review Findings — Independent Reassessment

**CR-01 (reviewer: Critical) — Gallery/logo SET_MEDIA dispatch lags one render behind the triggering click.**

Independently re-read `app/business/onboarding/AnalysoiSivusto.tsx:175-185`, `lib/livePreview/LivePreviewContext.tsx` (full file), and `app/business/onboarding/LivePreviewPane.tsx`.

**Finding: downgrade to Info. This is not a blocking defect.**

Reasoning:
- The effect-driven dispatch (`useEffect(() => dispatch(...), [selectedLogoUrl/selectedGallery, dispatch])`) fires within the same render-commit-effect cycle React produces for the click that changed the state. `dispatch` itself is guaranteed referentially stable (`useReducer`'s dispatch never changes — confirmed in `LivePreviewContext.tsx:172-175,186-191`), so the effect dependency array does not introduce any extra instability.
- For a single discrete click (the only realistic interaction — humans do not click two different gallery thumbnails within the same JS task), the user sees, at worst, one render where the just-updated thumbnail grid is visible but the live-preview pane has not yet re-rendered with the new media — and that gap closes within the same paint cycle in the overwhelming majority of cases, because React flushes effects synchronously after commit, before the next browser paint, for state updates originating from discrete user events. This is not a perceptible, reproducible visual bug.
- The reviewer's "compounds with rapid toggling" / "intermediate selections never reach the live preview" scenario describes two separate click events somehow batching into one effect run. Separate browser click events are dispatched as separate tasks; React's automatic batching merges multiple `setState` calls *within one event handler invocation*, not across two independent user clicks. As written, the escalation scenario does not describe a coherent failure mode — it conflates intra-handler batching with inter-event batching, which do not behave the same way.
- Critically, this pattern always **converges to the correct final state** — after the dust settles for any click, the dispatched payload always matches the latest `selectedGallery`/`selectedLogoUrl`. There is no permanent or compounding staleness, unlike the two prior Critical findings cited for comparison:
  - Phase 51's WR-01: a mount-time closure capturing values once, **never updating again** — permanent staleness for the component's entire lifetime.
  - Phase 51's CR-01: branding-path state **never threaded at all** — the preview would never reflect picks, a complete and total disconnect, not a timing nuance.
- The reviewer's own write-up concedes "a single extra render of staleness (cosmetic, arguably acceptable)" for the base case, which is itself an accurate characterization and should have been the final severity assessment rather than escalating on the basis of an internally inconsistent "rapid toggling" scenario.

**Recommendation:** Downgrade CR-01 from Critical to Info. Suggested remediation (non-blocking, can be deferred or folded into a future touch of this file): add a one-line comment near the two `useEffect`s acknowledging the dispatch trails the triggering render by one commit cycle, so a future reader doesn't need to re-derive this from scratch. No code change is required to satisfy the phase goal — "live preview reflects current state" is true within an imperceptible margin, not violated.

**WR-01 (reviewer: Warning) — `onReanalyze` does not reset `activeView` back to `'edit'`.**

Confirmed as a real, newly-introduced gap. Read `AnalysoiSivusto.tsx:955-971` directly: the `onReanalyze` closure resets `selectionInitialisedRef`, all selection state, `brandingResult`, and `phase`, but never calls `setActiveView('edit')`. This is new code introduced by this phase (the `activeView` state itself is new in 51.1-02) — not pre-existing. On mobile, a user who taps "Analysoi uudelleen" while on the `'preview'` tab will, once the new analysis completes and `phase` flips back to `'preview'`, land directly on the live-preview pane with no edit controls visible until they manually tap the toggle. This is a real, plausible UX dead-end, though recoverable with one extra tap (not a hard lock-out). Classified as a genuine **regression-shaped gap** introduced by this phase. Routed to human verification rather than treated as an automatic blocker, since its actual severity (one extra tap vs. perceived "stuck" screen) is a UX judgment call.

**WR-02 (reviewer: Warning) — new layout omits the `AnimatePresence` crossfade `WizardInner.tsx` uses for the same toggle.**

Confirmed accurate by direct comparison: `WizardInner.tsx:270-277` wraps its edit/preview toggle content in `<AnimatePresence mode="wait"><motion.div key={...} initial/animate/exit opacity transition duration:0.2>`. `AnalysoiSivusto.tsx`'s `PreviewPhaseContent` (lines 487-507) uses a bare ternary with no `AnimatePresence`/`motion` wrapper at all. This is a genuine, newly-introduced deviation from the plan's stated goal of replicating "the wizard's exact split-view (desktop)/toggle (mobile) layout" (CONTEXT.md D-02) — the desktop split is faithful, the mobile transition is not. Minor visual-polish gap, not a functional break (toggling still works, just abruptly instead of with a crossfade). Classified as a real but non-blocking warning.

**WR-03 (reviewer: Warning) — `onConfirm` invoked without awaiting/handling rejection in the click handler.**

Confirmed **pre-existing, not introduced by this phase**. `git show b80ed97~1:app/business/onboarding/AnalysoiSivusto.tsx` (the file state immediately before phase 51.1's changes) shows the identical `onClick={() => onConfirm(...)}` fire-and-forget call, byte-for-byte matching the post-phase code at lines 461-470. The PLAN explicitly required preserving this footer call "byte-for-byte" (51.1-02-PLAN.md Task 3 acceptance criteria), and the executor honored that. Not a regression; informational only.
