# Pitfalls Research

**Domain:** v3.0 "Oma tietokanta" — decommissioning Google Places as a data source, adding manual map-pin + Places Autocomplete location capture, extending the Claude branding-analysis prompt with sport-category inference, reworking claim/create onboarding with composite-unique constraints, and fixing the `/business` redirect-to-onboarding bug — all inside the existing Liikuntahakemisto codebase (Next.js 14 App Router, Supabase Postgres + RLS, `@vis.gl/react-google-maps`, `@anthropic-ai/sdk`).
**Researched:** 2026-06-22
**Confidence:** HIGH for schema/FK/cascade and codebase-specific pitfalls (direct inspection of migrations and routes); MEDIUM for the new Google Places `AutocompleteSuggestion`/Geocoding API integration (cross-checked against documented API shape and known migration guidance, not independently re-verified against the latest Google Maps Platform docs in this session — flag for phase-specific research before implementation); MEDIUM for Claude prompt-extension cost/schema-evolution pitfalls (general LLM structured-output practice, applied to this codebase's specific prompt).

This research supersedes the prior `PITFALLS.md` (which covered the v2.2 onboarding-AI milestone). It is scoped to the 5 risk areas named for v3.0: (1) deleting Google-sourced `liikuntapaikat` rows + decommissioning sync, (2) swapping to Places `AutocompleteSuggestion` + Geocoding inside the existing single `APIProvider`, (3) extending the branding-analysis Claude prompt additively, (4) reworking claim/create with separate company/branch names against the existing `UNIQUE(paikka_id)` constraint, (5) fixing the `/business` onboarding-redirect bug.

## Critical Pitfalls

### Pitfall 1: Deleting Google-sourced `liikuntapaikat` rows cascades silently through 5 dependent tables — and `business_managed=true` is not a safe "is this Google data" filter

**What goes wrong:**
Every FK from a dependent table to `liikuntapaikat(id)` in this schema is `ON DELETE CASCADE` — `reviews`, `suosikit`, `business_paikka_links`, `onboarding_draft`, and `business_branding.paikka_id` (added in `20260616100000_business_branding_plural_and_paikka_scoping.sql`) all cascade-delete the moment their parent `liikuntapaikat` row is deleted. There is **no FK-violation safety net** here — Postgres will happily delete a venue and silently take every review, every user's favorite, every business's claim/link, every in-progress onboarding draft, and all branding analysis with it. The milestone's stated plan ("delete all Google-Places-sourced rows") needs a row-selection filter, and the obvious candidate — `business_managed = false` — is **not actually "is this row Google-sourced."** `business_managed` is set to `true` by the approval trigger (`PUB-01`, `20260611000001_approval_trigger.sql`) whenever a `business_paikka_links.claim_status` transitions to `'approved'`, **regardless of whether the underlying `liikuntapaikat` row was originally inserted by `create-paikka` (truly new, business-authored) or `claim-paikka` (an existing, Google-sourced row a business successfully claimed)**. A bulk `DELETE FROM liikuntapaikat WHERE business_managed = false` is roughly correct as a first pass, but `DELETE FROM liikuntapaikat WHERE business_managed = true` being treated as "safe, these are business-owned, skip" is **wrong** for any row where `link_type = 'claim'` — those rows have real Google-sourced data (address, original opening hours, photos) sitting underneath a business claim, and the milestone's actual intent ("stop storing Google data") may or may not mean "also wipe the Google-origin fields on claimed venues," which is a product decision, not a `business_managed` boolean lookup.

**Why it happens:**
`business_managed` was designed for one purpose only — telling the sync script which rows *not to overwrite* (`DATA-09`). It was never designed to answer "did this row originate from Google Places or from a business." Reusing it for a decommissioning decision conflates two orthogonal questions: *who maintains this row going forward* vs *where did this row's original data come from*. The schema has no `data_origin` or `source` column that actually answers the second question.

**How to avoid:**
- Before writing any DELETE, determine row provenance from `business_paikka_links.link_type`: `'created'` rows are business-authored from day one (always safe to keep as-is, never Google data); `'claim'` rows have Google-origin base data even though `business_managed` may now be `true`. Rows with **no** `business_paikka_links` row at all are pure Google Places rows with zero business involvement — these are the actual "decommission" target.
- Write the cleanup migration as an explicit, reviewable SELECT-first script: `SELECT id, nimi, business_managed, (SELECT link_type FROM business_paikka_links WHERE paikka_id = liikuntapaikat.id) FROM liikuntapaikat` — categorize visually before deleting anything. Never run a bulk DELETE based on a single boolean without first listing affected row counts per category.
- For claimed (`link_type='claim'`) venues: decide explicitly whether to (a) leave the row as-is (business now owns/edits it going forward, Google-origin fields become stale-but-harmless), or (b) null out specific Google-origin fields (raw opening-hours-from-Places, etc.) while keeping the row and its FK-dependent reviews/favorites intact. Do NOT delete-and-recreate claimed venues — that destroys the `business_paikka_links` row (and its `claim_status` history) via cascade, forcing the business to re-claim/re-onboard from scratch.
- For pure-Google rows with no business link: confirm with the product owner whether existing `reviews`/`suosikit` referencing them should be preserved (e.g., by NOT deleting the row, just hiding it from new search via `published=false`) or genuinely purged (accepting the cascade loss of historical reviews). "Soft delete via `published=false`" avoids the cascade entirely and is reversible; a hard DELETE is not.
- Take a full `pg_dump` (or Supabase point-in-time-recovery checkpoint) immediately before running the production cleanup migration — this is a one-way door once cascades fire.

**Warning signs:**
- Cleanup migration or script written as a single `DELETE ... WHERE business_managed = false` with no dry-run SELECT and no row-count assertion before/after.
- No check of `business_paikka_links.link_type` anywhere in the decommission logic — treating `business_managed` as a proxy for "Google-sourced."
- `reviews` or `suosikit` row counts drop unexpectedly after the cleanup runs (cascade collateral damage, not intentional).

**Phase to address:**
Cleanup/decommission phase — must run **before** the sync route/cron removal, and must be its own reviewed phase, not folded into the location-step or claim-rework phases. This phase's plan should include an explicit row-count audit query as a UAT/verification step, not just "ran the migration, no errors."

### Pitfall 2: Removing `/api/admin/sync-paikat` removes the only code path that currently backfills `aukioloajat` for non-business venues — decommissioning before the manual-entry replacement exists creates a data gap

**What goes wrong:**
`DATA-01` ("Aukioloajat Google Places -haulla Supabaseen") and the existing `/api/admin/sync-paikat?kaupunki=` route are the **only** mechanism that populates/refreshes opening hours today for any venue not yet claimed by a business. If the sync route and its cron are decommissioned in the same phase (or before) the Google-sourced rows are deleted and the manual claim/create flow is reworked, there's a window where: any remaining Google-sourced venue that survives the cleanup (e.g., kept deliberately, or not yet decided) has **permanently stale, never-refreshing opening hours**, and any venue a business has not yet claimed has no path to get hours at all until they go through the new manual onboarding. If the milestone's intent is "100% business-entered data going forward," that's coherent — but it means the decommission phase must also decide and communicate **what happens to venues nobody has claimed yet** (do they get deleted outright per Pitfall 1, or do they remain in the directory indefinitely with frozen, aging hours data?). Removing the cron without an explicit decision here silently freezes data quality for an unbounded set of rows.

**Why it happens:**
"Remove Google Places sync" reads as a single atomic code-deletion task, but it's actually load-bearing for two different things that get conflated: (1) the automated *data-freshness* mechanism, and (2) the *initial data population* mechanism. Removing it solves "stop calling Google Places API" but doesn't by itself answer "what is now true about every row that this script used to keep fresh."

**How to avoid:**
- Decide and document, before writing the route-removal code: for venues with no business claim after cleanup, are they (a) deleted entirely (then this pitfall is moot — see Pitfall 1's provenance-aware deletion), (b) kept but flagged as "data may be outdated" in the UI, or (c) kept silently with no UI change (the dangerous default — stale-and-invisible).
- If any unclaimed venues are intentionally kept post-cleanup, add a `data_frozen_at` or similar timestamp column set at decommission time, so a future "how stale is our data" audit has a concrete anchor rather than relying on `updated_at` semantics that may not mean what they used to.
- Remove the cron trigger/schedule *before* removing the route code (verify nothing else still calls it — check Vercel cron config, GitHub Actions, or any external scheduler), then remove the route, then remove the `GOOGLE_PLACES_API_KEY` env var as the last step — this ordering means a accidental still-running cron fails loudly (404 route) rather than silently succeeding against a key that's about to be revoked.
- Search for any other consumer of `GOOGLE_PLACES_API_KEY` or the Places "search" (not Autocomplete) API before removing the key — confirm the v3.0 Autocomplete/Geocoding work uses a *different* key scope/API (it does, per the milestone's stated `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` client-side use) so revoking the old server-only key doesn't also break the new feature.

**Warning signs:**
- No decision recorded anywhere (PROJECT.md, REQUIREMENTS.md) about what state unclaimed-but-kept venues are left in.
- `aukioloajat` UI (the "Auki nyt" badge, `lib/aukiolo.ts` consumers) has no fallback/staleness messaging added even though its only data source is removed.
- Cron/schedule still configured to hit a route that returns 404 after removal (silent failure, no alert).

**Phase to address:**
Cleanup/decommission phase, sequenced explicitly *after* the row-deletion decision (Pitfall 1) is finalized — this phase should not start until "what happens to unclaimed venues" has a written answer.

### Pitfall 3: Loading the new Places `AutocompleteSuggestion` API alongside the existing single `APIProvider` risks double-loading the Maps JS API or loading the wrong library set

**What goes wrong:**
The app currently has exactly one `APIProvider` (`app/components/MapProvider.tsx`) wrapping the tree with `@vis.gl/react-google-maps`, and `MAP-03`'s explicit, hard-won requirement is "no double-load" of the Maps JS API (this was a known pitfall already solved once in this codebase). The new `AutocompleteSuggestion` API (the modern replacement for the deprecated `google.maps.places.Autocomplete` widget) requires the `places` library to be loaded via the Maps JS API loader, and the Geocoding API call can be done either client-side (`google.maps.Geocoder`, also requiring a loaded library) or server-side (REST call with a server key, no JS loader involved at all). The most common mistake when bolting a new Places feature onto an app that already has one `APIProvider`: adding a **second** `<APIProvider>` or a second manual `<script>` tag for the onboarding location step (because it's a different route/page than the main map and a contributor reaches for "just load it locally for this page"), which Google's loader explicitly warns against and which silently breaks because the global `google.maps` namespace gets initialized twice with conflicting library sets, causing one of the two consumers (likely the AdvancedMarker-based main map, given `MAP-03`'s constraint and the "AdvancedMarker migration is a Phase 7 prerequisite" note in CLAUDE.md) to fail unpredictably depending on load order.

**Why it happens:**
The onboarding location step is a different page/route than the consumer-facing map, so it's tempting to treat it as an independent feature needing its own Maps JS setup, especially since `@vis.gl/react-google-maps`'s newer Autocomplete-related hooks/components may be documented with their own standalone `<APIProvider>` example that doesn't account for an app that already has one wrapping the root layout.

**How to avoid:**
- Add `'places'` to the existing single `APIProvider`'s `libraries` prop (or equivalent `libraries={['places']}` parameter) rather than creating a second provider instance. Check `app/layout.tsx` / wherever `MapProvider` is mounted — if it currently wraps only specific routes rather than the root layout, the onboarding page must be inside that same provider tree, not a sibling with its own.
- If the onboarding wizard's location step lives under a layout that does NOT currently render inside `MapProvider`'s tree (e.g., `/business/onboarding` may not currently need the consumer map's provider), explicitly verify whether `/business/onboarding` is already inside the provider scope or needs the provider tree restructured — restructuring is the correct fix, a second provider is not.
- Use the `AutocompleteSuggestion`/`AutocompleteSuggestion.fetchAutocompleteSuggestions()` API (the 2024+ replacement), not the deprecated widget — confirm with current Google Maps Platform docs which `libraries` array entry it requires (this has shifted between `places` and a newer dedicated import in recent SDK versions; verify against the live docs before implementation, this is exactly the kind of detail that goes stale between this research pass and implementation).
- For Geocoding specifically: prefer the **server-side REST Geocoding API** call (using a server-side key with no HTTP referrer restriction, mirroring the existing `GOOGLE_PLACES_API_KEY` server-only pattern in this codebase) over the client-side `google.maps.Geocoder`, since the milestone explicitly wants "ephemeral-use" of Places data — doing the lookup server-side keeps the API key off the client entirely for that specific call and makes it trivial to enforce "we don't persist the raw Places response," matching CLAUDE.md's existing `GOOGLE_PLACES_API_KEY` server-only convention.

**Warning signs:**
- A new `<APIProvider>` JSX element anywhere outside `app/components/MapProvider.tsx`.
- A new `<script src="https://maps.googleapis.com/...">` tag added manually to any page.
- Console warning "You have included the Google Maps JavaScript API multiple times on this page" in dev/staging.
- The onboarding location step works in isolation during dev but the main consumer map breaks (or vice versa) only after both are loaded together in the same session — classic double-load symptom that single-page testing misses.

**Phase to address:**
Onboarding location-step phase — but the underlying provider/layout audit (does `/business/onboarding` sit inside the existing `APIProvider` tree?) should happen at the start of that phase, before any Autocomplete code is written, since it determines whether this is a one-line `libraries` prop change or a layout restructuring task.

### Pitfall 4: Places Autocomplete session tokens are easy to mismanage in a multi-step wizard, causing avoidable Places API billing as session-based (cheaper) pricing silently degrades to per-request pricing

**What goes wrong:**
Google's Places Autocomplete billing model is *session-based*: a session token groups the sequence of keystroke-driven autocomplete requests + the final Place Details/Geocoding call into one billed session, which is significantly cheaper than billing each autocomplete keystroke as an independent request. The session token must be (a) created once when the user starts typing, (b) reused across every subsequent suggestion request in that same search, and (c) only consumed/finalized when the user selects a suggestion and the place-details/geocode call fires — then a **new** token must be created for the next search. Inside a React wizard step with re-renders (this codebase already has documented re-render-care patterns elsewhere — see the live-preview architecture in PROJECT.md's decision log), the most common mistakes are: (1) creating a brand-new session token on every keystroke/re-render instead of once per search session — every autocomplete request bills as if it were its own session, multiplying cost; (2) never finalizing/consuming the token (forgetting to pass it to the Geocoding/Place Details call) — the session technically never completes, and depending on Google's billing reconciliation this can also default to per-request billing; (3) reusing the *same* token across multiple unrelated searches (e.g., user types an address, clears it, types a different address, but the component never creates a new token) — this also breaks the cost model's assumptions and may violate the Places API Terms of Service requirement that a session token represent one user-intent search.

**Why it happens:**
Session tokens are an easy detail to omit because Autocomplete *works* functionally without them (suggestions still appear) — the cost-model breakage is invisible until a Google Cloud bill arrives, and there's no test that fails if you skip token management. React's re-render lifecycle (a step component remounting, or local state being reset on step navigation) is also a natural place for a token created in `useState` to silently get recreated when a developer didn't intend it to.

**How to avoke:**
- Create the session token in a `useRef` (not `useState`) scoped to the address-input component's lifetime, so it survives re-renders without being recreated — only construct a new token explicitly on user-initiated events: first keystroke of a fresh search, or after a place is selected and the user starts a new search.
- Explicitly pass the token to BOTH the autocomplete-suggestions call and the subsequent Geocoding/Place Details call that resolves the selected suggestion to lat/lng — this is the step most likely to be missed since it's a separate API call than the one that obviously "needs" the token.
- After a suggestion is selected and resolved, null out the ref (or generate the next token immediately) so the next search starts clean — don't let a stale, already-consumed token get reused for an unrelated subsequent search.
- If the address-input is unmounted/remounted across wizard steps (e.g., user goes back to the location step after navigating forward), verify whether the token should reset (new step entry = new session) — the safest default for ToS compliance is "new component mount = new token."
- Log/monitor actual Places API costs for the first weeks after launch (Google Cloud Console billing reports broken down by API) to catch token mismanagement empirically, since there's no functional test that distinguishes "10 cheap session-billed searches" from "100 keystroke-billed requests" — both produce working autocomplete UI.

**Warning signs:**
- Session token created with `useState(() => new google.maps.places.AutocompleteSessionToken())` with no guard against recreation on re-render (initializer functions in `useState` only run once on mount, which is actually safe — but verify this isn't refactored later into a plain `new AutocompleteSessionToken()` call inline in the render body, which WOULD recreate on every render).
- The Geocoding/Place Details call after suggestion-selection does not include the same token object that was used for the preceding suggestion requests.
- No cost monitoring/alerting set up before this ships to production — first signal of misuse becomes the monthly bill, not a dev-time warning.

**Phase to address:**
Onboarding location-step phase — token lifecycle should be designed alongside the Autocomplete component itself, not retrofitted after a billing surprise.

### Pitfall 5: Storing more from the Places Autocomplete/Geocoding response than "lat/lng + user-typed address" violates Google's Terms of Service caching/storage restrictions

**What goes wrong:**
The milestone explicitly states "ephemeral-käyttö" (ephemeral use) and "tallennetaan vain lat/lng + käyttäjän kirjoittama osoite" (only lat/lng + the user's own typed address are persisted) — this is the correct intent, but it's easy to violate accidentally because the Places API response objects (`AutocompleteSuggestion`, Place Details, Geocoding results) carry a rich `place_id`, formatted address, address components, and other metadata that's *convenient* to just spread into the database row "while we're at it" (e.g., to also auto-fill a `kaupunki` field from Google's returned city component, or to store the `place_id` for "future re-geocoding"). Google's Places API Terms of Service place specific restrictions on caching/persisting Place IDs and Places data beyond short-lived, allowed use cases (the exact allowed-caching rules differ by which API/SKU is used and have changed across Platform ToS versions) — persisting a `place_id` indefinitely in `liikuntapaikat` without checking the current ToS caching policy for the specific Places SKU used here is a plausible compliance violation, not just a style nitpick.

**Why it happens:**
"We already have the data in the response, storing it is free (in code terms)" is the natural engineering instinct, and the city/postal-code fields Google returns look strictly more useful than asking the business to retype them — but "useful" and "ToS-compliant to store" are different questions, and the milestone's explicit "lat/lng + user-typed address only" framing already encodes someone having thought about this constraint once; the risk is a future PR or even a same-phase refactor reintroducing convenience fields without re-checking the constraint.

**How to avoid:**
- Write the storage boundary as a code-level contract, not just a design intention: the API route/handler that receives the Autocomplete/Geocoding result should destructure and persist ONLY `{ lat, lng }` plus the address string the *user typed or edited* (not Google's "formatted_address"), and should not pass the raw API response object (or `place_id`) anywhere near a Supabase write call.
- If a `place_id` or any other Places-specific field is genuinely needed later (e.g., to re-geocode if a venue moves), confirm against the **current** Google Maps Platform Terms of Service / Places API caching policy before adding a column for it — this is a legal/compliance check, not an engineering one, and should not be inferred from old blog posts or this research pass alone (ToS terms have changed multiple times; verify against the live policy page at implementation time).
- Code review checklist item for this phase specifically: "does this PR introduce a new column or persisted field derived from a Places API response field other than lat/lng and the user-edited address string?" — if yes, flag for explicit ToS review before merging.
- Apply the same discipline already established in this codebase for a different third-party-data-storage concern (`SEC-46-02`: never store/serve raw third-party image URLs, always proxy through Supabase Storage) — the underlying principle ("don't let third-party API response shapes leak into our persisted schema unreviewed") is the same one, just for a different vendor and data type.

**Warning signs:**
- A new migration adds a `place_id`, `google_formatted_address`, or similar column to `liikuntapaikat` without an accompanying note about why it's ToS-compliant to store it.
- The location-step API route passes the entire Geocoding/Place Details response object to a Supabase insert/update call rather than a destructured `{ lat, lng, osoite }` shape.
- `kaupunki` gets auto-populated from a Places address component rather than the existing pattern (user-selected from a known city list, per `DATA-07`).

**Phase to address:**
Onboarding location-step phase — the storage contract should be code-reviewed explicitly against this constraint before merge, since it's the kind of mistake that ships looking correct (the feature works) and is only caught by a ToS audit or a Google enforcement action later.

### Pitfall 6: Extending the branding-analysis prompt to also output a sport-category guess breaks existing JSON parsing if the schema change isn't purely additive — and the prompt is already mid-evolution (screenshots, plural logos/colors) from a recent phase

**What goes wrong:**
`lib/branding/prompt.ts` (current `BRANDING_ANALYSIS_PROMPT`) already specifies an exact JSON shape (`logos[]`, `colors[]`, `prices[]`, `opening_hours[]`, `website_url`) that `lib/branding/analyzer.ts` parses with field-specific validation (bounds-checking `logo_index`-equivalents, filtering `colors` to valid hex, etc. — per the prior PITFALLS.md's Pitfall 7 finding that this validation already has narrow assumptions baked in). Adding a sport-category guess (`"laji": "..."` or similar) to this same single Claude call risks two distinct failure modes if not done carefully: (1) **schema drift** — if the new field is added to the prompt's example JSON but the corresponding TypeScript type/Zod-equivalent validator in `analyzer.ts` isn't updated in the same change, a successful Claude response with the new field present will either be silently dropped (if parsing is permissive) or cause a hard parse/validation failure (if parsing is strict) for 100% of analyses going forward, not just the ones involving sport-category — this is a full-feature regression risk for an unrelated, already-shipped capability (logo/color/price/hours extraction), not just a "new field doesn't work yet" risk; (2) **prompt-quality interference** — Claude's structured-output quality for the existing fields can measurably degrade when an unrelated extraction task is added to the same call, especially for a small/fast model (this codebase explicitly uses Claude for a single combined vision+text call already optimized for cost — check whether it's Haiku per the AI-01 pattern elsewhere in this app); adding "also guess the sport/category from the page content" competes for the model's attention budget against "carefully extract exact prices and hours," and the JSON-shape instructions get longer and more complex, which increases the chance of malformed output (extra commentary, wrong field nesting) even when the model "knows" the right category.

**Why it happens:**
"Add one more field to the JSON the AI already returns" looks like a one-line prompt edit, but the prompt and its parser are a tightly coupled contract (the prior PITFALLS.md already flagged this exact class of risk for the `colors` array), and sport-category classification is a *qualitatively different* task (classification into a known taxonomy) from the existing tasks (extraction/transcription of literal page content) — it has different failure modes (e.g., "what if the page describes 3 different sports the venue offers" has no clean single-value answer, whereas "what's the hex code of this button" does).

**How to avoid:**
- Add the new field as a genuinely optional, independently-parseable addition: `"sport_category": { "guess": <string from the existing lib/lajit.ts taxonomy>, "confidence": "high" | "medium" | "low" }` (or similar) — and write the analyzer-side type/validator change in the SAME commit/PR as the prompt change, with a test asserting that a Claude response missing the new field (simulating a model that ignores the new instruction) still parses successfully for all the pre-existing fields. This is the actual "additive, not breaking" verification — not just "I added the field to the prompt text."
- Constrain the sport-category guess to the **existing** `lib/lajit.ts` taxonomy explicitly in the prompt (enumerate the valid category strings inline, the same way `opening_hours.day` is constrained to `Ma, Ti, Ke, To, Pe, La, Su` today) rather than letting Claude free-text a category name — free-text categories require a separate fuzzy-matching/normalization step before they're usable as a `laji` value, which is unnecessary complexity given the taxonomy already exists and is small.
- Run a before/after eval on a fixed set of real onboarding-analysis inputs (reuse any existing test fixtures from the v2.1/v2.2 phases if they exist) comparing extraction quality for logos/colors/prices/hours before and after the prompt change, not just "does the new field work" — this catches attention-budget degradation that a feature-only test would miss.
- Per the milestone's own framing ("käyttäjä vahvistaa/muuttaa" — user confirms/changes), treat the sport-category guess as a **suggestion with a mandatory confirm-or-edit UI step**, never auto-applied to `liikuntapaikat.laji` without the business explicitly confirming — this is both a UX requirement already stated and a pragmatic mitigation for low classification confidence on ambiguous venues (e.g., a multi-sport facility).
- Be aware the prompt is mid-evolution already — `prompt.ts`'s own header comment notes a dependency on the scraper sending labeled screenshots (`SCRAP-08`) that may not be fully wired yet ("Jos scraper ei vielä lähetä screenshotteja..."). Confirm the current actual state of that dependency before treating the prompt as a stable base to extend — if screenshots aren't yet flowing, color-extraction quality is already degraded independent of this milestone's change, and that pre-existing gap shouldn't be conflated with new regressions from the sport-category addition.

**Warning signs:**
- A PR that edits `lib/branding/prompt.ts`'s example JSON shape without a corresponding diff in `lib/branding/analyzer.ts`'s parsing/validation code in the same commit.
- No before/after comparison of logo/color/price/hours extraction accuracy on any fixture after the prompt change ships — only the new sport-category field gets tested.
- Sport-category guess written directly to `liikuntapaikat.laji` in the onboarding save-step flow with no visible confirm/edit UI step, contradicting the milestone's own "käyttäjä vahvistaa/muuttaa" framing.

**Phase to address:**
AI-sivuanalyysi-laajennus phase (the dedicated phase for this feature) — but the analyzer-side type/validator update must land in the same phase/PR as the prompt change, not deferred, and a regression check against existing extraction fields should be a named verification step in that phase's plan.

### Pitfall 7: Reworking claim/create with separate company-name + branch-name fields collides with the existing `UNIQUE(paikka_id)` constraint on `business_paikka_links` — multi-venue and chain scenarios are not currently representable

**What goes wrong:**
`business_paikka_links` has an explicit, deliberately-added `UNIQUE INDEX business_paikka_links_paikka_id_unique ON business_paikka_links(paikka_id)` (`20260610000005_confirm_paikka_unique.sql`), whose own migration comment states its purpose: prevent two different businesses from both holding a `'pending'` (or any) link to the same venue, which is the core "Jo hallittu" (already-claimed) invariant. This constraint is **on `paikka_id` alone**, not a composite `(business_account_id, paikka_id)` — meaning the *current* schema already enforces "one venue, one business, ever" globally, not just "one venue, one business, while pending." If the claim/create rework introduces any scenario where the *same business* might legitimately want multiple link rows for the *same* venue (e.g., a reapply-after-rejection that — per the existing decision — correctly reuses UPDATE rather than INSERT specifically *because* of this constraint, per the Key Decisions log: "Reapply: UPDATE rejected → pending (ei INSERT) — Composite UNIQUE rajoite... uusi INSERT rikkoisi sen"), the new "create from scratch with separate company-name/branch-name fields" flow must preserve this exact invariant or it will hit unique-violation errors (Postgres code `23505`, already handled in `claim-paikka/route.ts` for the claim path) in code paths that don't currently expect it. Specifically: if "create a venue from scratch" in the new flow is reworked to support a business creating *multiple branches* (the company-name/branch-name split strongly implies multi-branch intent — "Ketjuadmin" chain-admin support is explicitly listed as a deferred-but-anticipated future feature in PROJECT.md), each new branch is still a **new** `liikuntapaikat` row with its own `paikka_id`, so the existing per-venue uniqueness still holds *naturally* — but if the rework instead tries to link one `business_account_id` to multiple `paikka_id` rows that represent the *same physical location* under the new naming scheme (e.g., re-creating "the same place" because the old single-name model is being migrated to the new two-field model), that's where the constraint becomes a hazard: any code path that does INSERT-after-existing-claim (rather than UPDATE, like reapply correctly does) will throw 409s in places nobody tested for, or — worse — a developer "fixes" the 409 by changing the constraint to be business-scoped instead of global, silently reintroducing the exact double-claim bug the constraint was added to prevent (T-33-03-04 era).

**Why it happens:**
"Add a company-name + branch-name field pair" reads as a pure UI/form change, but it's actually a data-model question in disguise — it changes what "a venue" and "an account" represent in relation to each other, and the existing schema's uniqueness invariant was tuned for a 1-business-1-venue-at-a-time mental model that the new naming scheme implicitly gestures toward (without this milestone necessarily intending to) multi-branch support.

**How to avoid:**
- Explicitly scope the rework: does "separate company-name + branch-name fields" mean (a) purely cosmetic — one business, one venue per claim/create flow still, just better-labeled name fields stored as two columns or one normalized string on the same `liikuntapaikat` row, with `business_paikka_links`'s existing 1:1-per-venue constraint untouched — or (b) a precursor to true multi-branch support where one company entity can own several branch rows? If (a), the existing `UNIQUE(paikka_id)` constraint needs zero changes — just add `company_name`/`branch_name` columns (or a single normalized `nimi` built from both) to `liikuntapaikat` or `business_accounts` as appropriate, and this pitfall doesn't materialize. If (b), this milestone is implicitly starting the chain-admin work that PROJECT.md explicitly defers — flag this scope creep to the user/PROJECT.md before building it.
- If two name fields are stored, decide where: `company_name` likely belongs on `business_accounts` (one company, already 1:1 with `user_id`) while `branch_name` (or the full venue display name) belongs on `liikuntapaikat.nimi` as today — don't add both fields redundantly to both tables, which creates a sync-drift risk (which name wins when they disagree?).
- Any new code path that writes to `business_paikka_links` (beyond the existing `claim-paikka`, `create-paikka`, `reapply` routes) must explicitly handle the `23505` unique-violation the same way `claim-paikka/route.ts` already does (returns 409 "Already claimed") — copy that error-handling pattern, don't assume INSERT will succeed.
- Add an explicit test: business A creates venue 1 with company-name "Acme" / branch-name "Acme Tampere"; business A attempts to create a second venue reusing the same company-name — assert this succeeds (different `paikka_id`, no constraint conflict) — and a *different* business B attempts to claim/create against an existing `paikka_id` business A already owns — assert this still 409s exactly as it does today, proving the rework didn't accidentally loosen the per-venue uniqueness.

**Warning signs:**
- Migration that touches `business_paikka_links`'s unique constraint (widening it to a composite key, or dropping it) without an explicit, separately-reviewed justification — this constraint exists for a specific anti-double-claim reason and should not be casually adjusted as a side effect of a naming-field change.
- New write path to `business_paikka_links` that doesn't handle Postgres error code `23505`.
- "Branch name" UI copy in the new flow that implies multi-branch chain support when the underlying schema/constraint work for that hasn't been scoped or decided.

**Phase to address:**
Claim/create rework phase — the company-name/branch-name schema decision (cosmetic vs. multi-branch precursor) must be made explicit and written into PROJECT.md's Key Decisions log *before* the migration is written, given the existing precedent of every other schema decision in this codebase being logged with rationale.

### Pitfall 8: Reworking claim/create mid-onboarding for *existing* business accounts risks corrupting in-flight `onboarding_draft` rows and previously-submitted-but-pending links

**What goes wrong:**
At the moment this rework ships, there may be business accounts with: (a) an `onboarding_draft` row keyed to a `paikka_id` created under the OLD claim/create flow (single name field, found-or-created via the old `ClaimSearchForm`/`create-paikka` shape), still mid-wizard; (b) a `business_paikka_links` row with `claim_status = 'pending'` awaiting admin approval, created under the old flow's field shape; (c) a `business_paikka_links` row with `claim_status = 'rejected'`, eligible for reapply via the existing UPDATE-not-INSERT pattern. If the new claim/create flow changes what fields are collected (company-name + branch-name instead of one `nimi`) and what gets written to `liikuntapaikat` at creation time, but the migration doesn't backfill or reconcile existing rows created under the old shape, then: draft (a) resuming after deploy may present a wizard UI built for the new two-field model against `liikuntapaikat.nimi` data that was written as a single combined string — the new edit UI has nowhere obvious to split "Acme Tampere Oy — Keskusta" back into `company_name`/`branch_name` automatically, and a naive "just show the old combined nimi in the new branch_name field, leave company_name empty" silently produces ugly/wrong display once company_name starts being rendered separately elsewhere (e.g., in admin queue, business dashboard). Pending row (b) sitting in the admin queue at deploy time will be reviewed by an admin who may now see a UI built for the new fields with old-shape data underneath — same display-mismatch risk, but visible to a different actor (admin, not the business) and at a moment (approval decision) where bad data presentation has higher consequence than a self-service draft. The existing reapply UPDATE pattern (b)/(c) is itself unaffected by this rework *structurally* (it still just flips `claim_status`), but if the rework changes what `business_paikka_links` or `liikuntapaikat` columns mean, the data the reapplying business sees pre-filled (if any pre-fill exists) may be stale/wrong-shaped too.

**Why it happens:**
A schema/field-shape rework is naturally designed and tested against fresh accounts created after deploy — the existing-in-flight-account case requires deliberately writing a backfill/migration step and a deploy-day data audit, which is easy to skip because "it's not a new-user-facing change" rationalization undercounts how many users are mid-flow at any given moment in a live, already-shipped onboarding system (per CLAUDE.md/PROJECT.md, this product has had real business onboarding traffic since v1.7).

**How to avoid:**
- Before deploy, query production for all `onboarding_draft` rows (any status), all `business_paikka_links` rows with `claim_status IN ('pending', 'rejected')`, and count them — this tells you the actual blast radius, not a hypothetical one.
- Write an explicit backfill migration for the field-shape change: attempt to split existing single-`nimi` values into best-guess `company_name`/`branch_name` (or, more conservatively, just copy the existing `nimi` into BOTH new fields as a safe default, flagged for the business to correct on their next dashboard visit) — don't leave the new field NULL for pre-existing rows, which is worse for display than a redundant-but-non-empty guess.
- For pending admin-queue rows specifically: either (a) process/clear the admin queue to zero before deploying the rework (operationally simplest if the queue is small, which is plausible at this product's current scale), or (b) ensure the admin review UI gracefully falls back to showing the old-shape `nimi` field when `company_name`/`branch_name` are both empty, rather than rendering blank/broken fields.
- Treat this exactly like the prior PITFALLS.md's already-identified "draft step-reorder breaks resuming an old draft" pattern (Pitfall 2 in that document) — same root cause class (persisted state shape changes under a live system), same prevention strategy (detect pre-migration rows via timestamp/version, force a safe path rather than silently misrendering).

**Warning signs:**
- Migration adds `company_name`/`branch_name` columns with no `UPDATE ... SET company_name = nimi, branch_name = nimi WHERE company_name IS NULL`-style backfill statement.
- No pre-deploy query/count of affected in-flight rows performed or documented in the phase's verification notes.
- Admin queue UI assumes `company_name` is always populated post-deploy without a fallback render path.

**Phase to address:**
Claim/create rework phase — the backfill migration and a pre-deploy production audit query should be an explicit, named step in that phase's plan, not an afterthought discovered during execution.

### Pitfall 9: Fixing the `/business` redirect-to-onboarding bug by adding a new condition risks an infinite redirect loop or silently stranding genuinely-new businesses on the dashboard

**What goes wrong:**
The current `/business/page.tsx` logic is: if the user has a `business_accounts` row AND has at least one `onboarding_draft` row (any status, any venue), redirect to `/business/onboarding`; otherwise, render the dashboard (showing claimed venues, or a bare claim form if `venueLinks.length === 0`). The milestone's stated bug ("never auto-redirect to onboarding; an incomplete onboarding can be resumed from `/business` by selecting the venue, shown with an in-progress indicator") describes a **behavior change**, not just a bug fix to existing logic — the fix needs to (a) remove the unconditional auto-redirect entirely, (b) add UI on the dashboard to show in-progress venues with a "kesken" (incomplete) badge and a way to resume, and (c) crucially, **still get genuinely brand-new businesses (zero venues, zero drafts) to the right starting point**, since `/business/page.tsx`'s third render branch (no `venueLinks`, falls through to bare `ClaimSearchForm`) currently assumes the *old* claim/create flow as the default "new business" landing experience — but per the milestone, claim/create is also being reworked in this same v3.0 cycle. The actual risk here isn't infinite redirects in the technical sense (no code currently round-trips `/business` → `/business/onboarding` → `/business`) but rather: (1) a poorly-scoped fix that removes the redirect but doesn't add the promised "select venue from dashboard to resume" UI, silently stranding a business with an in-progress draft on a dashboard that shows nothing actionable for it (worse than the current bug, which at least gets them back into the wizard automatically); (2) the interaction between "remove auto-redirect" and the claim/create rework shipping in the same milestone — if claim/create's entry point changes (e.g., new fields, new route), the dashboard's fallback "new business, no venues yet" branch must be updated in lockstep, or new businesses landing on `/business` for the first time see a stale claim-form UI that doesn't match the reworked flow, or worse, a broken one if routes/props changed.

**Why it happens:**
"Don't redirect automatically" sounds like a one-line conditional removal, but the redirect was doing real work (getting users with incomplete state to the right screen) that needs an equivalent *replacement* UI, not just deletion — and because this fix and the claim/create rework are scoped to the same milestone, the "what does `/business` show a venue-less new business" question gets answered twice (once implicitly by removing the auto-redirect, once by the rework changing what claim/create looks like) unless explicitly coordinated.

**How to avoid:**
- Treat this as 3 distinct, testable states for `/business`, not a single redirect-or-not branch: (1) zero venues, zero drafts → show the (reworked) create/claim entry point inline, no redirect; (2) ≥1 `onboarding_draft` row exists for ≥1 venue → show those venues in the dashboard list with an explicit "kesken" badge and a button/link that navigates to `/business/onboarding?paikka_id=X` for that specific draft (reusing the existing `paikka_id` URL-param pattern already established per the Key Decisions log: "paikka_id URL-parametrina edit/onboarding-velhossa"), never an automatic `useEffect` redirect; (3) ≥1 fully-submitted/approved/rejected venue with no pending draft → existing dashboard behavior, unchanged.
- Write this as explicit test cases before implementation, each asserting what `/business` renders for a given account state — particularly state (2) with **multiple** simultaneous drafts (the existing comment in `page.tsx` already notes "This handles both first-time users and multi-venue users mid-onboarding," meaning multi-draft accounts are an anticipated case, not an edge case) — verify the new "kesken" list UI handles 2+ in-progress drafts distinctly, not just a single boolean "has a draft, redirect" check collapsed into a single badge.
- Coordinate explicitly with the claim/create rework phase: if that phase changes the create-entry-point's route, props, or required fields, the `/business` dashboard's "no venues yet" branch (currently `<ClaimSearchForm />` rendered inline) must be updated in the SAME phase as the rework, or sequenced so the redirect-fix phase lands strictly after the rework phase, never before (building the new "kesken" resume UI against entry points that are about to change underneath it is wasted/throwaway work).
- Explicitly test the "no infinite loop" property even though current code doesn't have a back-edge: once `/business/onboarding` is reached via the new resume button (not auto-redirect), confirm `/business/onboarding` itself has no logic that redirects back to `/business` under any circumstance that could re-trigger a "kesken" state loop (e.g., if onboarding's own guard logic checks for an account+draft mismatch and bounces back to `/business` on some error path — audit that page too, not just the one being fixed).

**Warning signs:**
- The fix PR diff is a single removed `useEffect`/`router.push` call with no corresponding new UI added in the same diff — incomplete fix, stranding users.
- No test or manual QA step covers "account with 2 simultaneous in-progress drafts for 2 different venues."
- The redirect-fix phase is scheduled/executed before the claim/create-rework phase, creating throwaway work when the rework lands.
- `/business/onboarding`'s own internal guard logic (not just `/business/page.tsx`) isn't audited for a reciprocal redirect-back-to-`/business` condition.

**Phase to address:**
Should be the LAST phase of this milestone, explicitly sequenced after the claim/create rework — fixing the redirect against entry points that are about to change is wasted effort and risks re-fixing it twice. If sequencing forces it earlier for some reason, the phase plan must explicitly flag the entry-point coupling as a known re-touch point.

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|--------------|------------------|---------------------|
| Postgres `ON DELETE CASCADE` FKs (`reviews`, `suosikit`, `business_paikka_links`, `onboarding_draft`, `business_branding`) | Assuming deletion will be blocked/visible if dependents exist | Cascades are silent and immediate — always SELECT-and-count dependents before any bulk DELETE on `liikuntapaikat` |
| `@vis.gl/react-google-maps` `APIProvider` + new Places `AutocompleteSuggestion` | Adding a second provider/script tag for a new page/route | Add `'places'` (or the current required library name — verify against live docs) to the existing single `APIProvider`'s `libraries` prop; restructure layout scope if the new page isn't inside the existing provider tree |
| Places Autocomplete session tokens | Creating a new token per keystroke/render, or never passing it to the final Geocoding/Place Details call | One token per user search-intent, created once via `useRef`, passed to both the suggestions call and the resolving call, then discarded |
| Places/Geocoding API response storage | Persisting `place_id` or other vendor metadata fields beyond lat/lng + user-typed address | Destructure only `{ lat, lng, osoite }` before any Supabase write; treat ToS caching restrictions as a compliance gate, verified against current policy at implementation time |
| Claude structured-output schema evolution (`lib/branding/prompt.ts` + `analyzer.ts`) | Editing the prompt's example JSON without updating the parser/validator in the same change | Ship prompt + parser changes in one commit; test that a response missing the new field still parses all pre-existing fields successfully |
| `business_paikka_links.UNIQUE(paikka_id)` | Adding a new write path (e.g., for reworked create flow) that assumes INSERT will always succeed | Always handle Postgres `23505` the same way `claim-paikka/route.ts` already does; never widen/drop this constraint without explicit, separate review |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|-----------|------------|------------------|
| Per-keystroke Places Autocomplete requests with mismanaged session tokens | Google Cloud Places API billing line item grows much faster than actual user search volume would suggest | `useRef`-scoped session token, created once per search, reused across suggestion calls, passed to the final resolving call | Noticed only when the monthly bill arrives unless cost monitoring/alerting is set up at launch — not a "scale" threshold, an immediate-from-day-one risk |
| Concatenating sport-category classification into the same single Claude call without re-checking output-token budget | Existing `max_tokens` cap (if unchanged) silently truncates output once the response JSON grows with the new field, corrupting JSON parsing for ALL fields, not just the new one | Verify the existing `max_tokens` setting in `analyzer.ts` accounts for the marginal token cost of the new field; add response-truncation detection (e.g., JSON.parse failure handling) if not already present | As soon as the prompt change ships, if `max_tokens` isn't re-evaluated — this is immediate, not gradual |
| Bulk DELETE on `liikuntapaikat` cascading through 5 dependent tables in one transaction | Migration/cleanup script takes much longer than expected, or locks tables under concurrent traffic if run during business hours | Run the cleanup during a low-traffic window; consider batching deletes (e.g., by city or by id range) rather than one unbounded DELETE if the row count is large enough to matter | Scales with total row count of Google-sourced venues × average dependents per row — check actual production row counts before assuming "small dataset, no batching needed" |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| Treating `business_managed = true` as proof a row has no Google-sourced data underneath | Data-provenance confusion leads to incorrect cleanup decisions (keeping data that should be removed, or removing data tied to a live business claim) | Always cross-reference `business_paikka_links.link_type` before any provenance-based decision |
| Storing the full Places API response (including `place_id`) instead of just lat/lng + user-typed address | Plausible Google Maps Platform Terms of Service violation around Places data caching/persistence | Destructure to the minimal allowed shape before any DB write; verify current ToS at implementation time, not from this research alone |
| Client-side Geocoding API calls using a client-exposed key for a flow the milestone wants "ephemeral" | Slightly weaker control over what's logged/cached client-side compared to a server-side call | Prefer server-side REST Geocoding with a server-only key (mirroring the existing `GOOGLE_PLACES_API_KEY` server-only convention), especially given the explicit "ephemeral-use" framing |
| New `business_paikka_links` write path (from the claim/create rework) that doesn't reuse the existing JWT-verify + ownership-check pattern already established in `claim-paikka`/`create-paikka`/`reapply` routes | Elevation-of-privilege — a business could write a link/venue under another account's identity if a new route skips the `supabaseAdmin.auth.getUser(token)` pattern | Copy the existing verified-JWT pattern exactly for any new write route introduced by the rework; never trust client-supplied `business_account_id` |
| Sport-category AI guess written directly to `liikuntapaikat.laji` without confirm step, then exposed publicly via search/filter UI | Low-severity but real data-quality/trust issue — wrong public-facing category data, not a security breach but a correctness/trust failure with similar "looks done but isn't" risk profile | Treat as user-confirmed data only; never auto-publish an unconfirmed AI guess to a publicly-filterable field |

- [ ] **Google-data cleanup:** Looks done when `liikuntapaikat` row count drops and the admin confirms "looks right" — verify `reviews`/`suosikit`/`business_paikka_links` row counts were audited before AND after, and that `link_type='claim'` rows were explicitly excluded from blind `business_managed`-based deletion logic.
- [ ] **Sync route/cron decommission:** Looks done when the route returns 404 and no errors appear — verify the cron schedule/trigger itself was also removed (not just the route), and that a decision exists for what happens to any venue still relying on frozen Google-sourced hours data.
- [ ] **Places Autocomplete integration:** Looks done when suggestions appear while typing — verify only one Maps JS API load occurs (check Network tab / console for double-load warnings) across BOTH the consumer map and the new onboarding location step in the same browser session.
- [ ] **Session token management:** Looks done when autocomplete works and a place can be selected — verify (via Google Cloud Console billing reports after a few days of real usage, not just functional testing) that requests are being billed at session-based rates, not per-keystroke rates.
- [ ] **Location data storage:** Looks done when lat/lng saves correctly — verify the actual Supabase row/migration contains ONLY lat/lng + user-typed address, with no `place_id` or other raw Places response fields persisted anywhere.
- [ ] **Sport-category prompt extension:** Looks done when the new field appears in Claude's JSON response during manual testing — verify existing logo/color/price/hours extraction quality wasn't regressed (compare against pre-change fixtures), and that the new field is constrained to the existing `lib/lajit.ts` taxonomy, not free text.
- [ ] **Claim/create rework with company/branch fields:** Looks done when a brand-new business can create a venue with both fields — verify existing in-flight `onboarding_draft`/pending/`rejected` rows from before the rework were backfilled or explicitly handled, not left to render blank fields.
- [ ] **`business_paikka_links` constraint integrity:** Looks done when the new create flow inserts successfully for fresh test accounts — verify the existing `UNIQUE(paikka_id)` constraint still rejects a second business claiming/creating against an already-linked `paikka_id` with the same 409 behavior as today.
- [ ] **`/business` redirect fix:** Looks done when a fresh test account no longer auto-redirects — verify an account with 2+ simultaneous in-progress drafts renders a usable "kesken" list (not just a single boolean badge), and that this was tested AFTER the claim/create rework's entry-point changes landed, not against the old entry point.

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|----------------|--------------------|
| Wrong rows deleted from `liikuntapaikat` during cleanup (cascade took dependents with it) | HIGH | Restore from `pg_dump`/point-in-time-recovery taken immediately before the migration; if no backup exists, this is unrecoverable for cascaded reviews/favorites — re-emphasizes the mandatory pre-migration backup step |
| Sync cron removed before deciding what happens to unclaimed venues, hours data visibly stale in production | LOW–MEDIUM | Add a UI staleness indicator retroactively, or run the cleanup decision (delete vs. keep) after the fact — this is a config/UI fix, not a schema fix, if caught reasonably early |
| Double Maps JS API load discovered in production (console warnings, intermittent map breakage) | LOW–MEDIUM | Consolidate to the single existing `APIProvider`, remove the duplicate provider/script tag; usually a quick, localized fix once identified, but may require auditing every page for the duplicate load source |
| Places API billing spike discovered from a monthly bill (session token mismanagement) | LOW (engineering) / MEDIUM (cost, already incurred) | Fix token lifecycle going forward (cannot retroactively reduce already-billed usage); add cost alerting so the next regression is caught in days, not a month |
| `place_id` or other Places metadata discovered already persisted in production, ToS-compliance concern raised | MEDIUM | Migration to drop the offending column(s) after confirming no feature depends on them; audit how long the data was stored and whether disclosure/cleanup obligations apply |
| Sport-category prompt change degraded existing logo/color/price/hours extraction quality | LOW–MEDIUM | Revert the prompt change or restructure (e.g., move sport-category to a separate, smaller follow-up Claude call) if attention-budget competition is confirmed as the cause; this is a prompt-engineering fix, not a schema fix |
| Pre-existing in-flight business accounts see broken/blank fields after the company/branch-name rework ships without backfill | LOW–MEDIUM | Run the backfill migration after the fact (copy `nimi` into both new fields for any row still NULL); notify affected businesses via email if any have already submitted with blank fields, ask them to confirm/correct |
| `/business` redirect fix shipped without the replacement "kesken" UI, businesses report being stuck | LOW | Fast-follow PR adding the resume UI; this is additive, not a data issue, so recovery is just shipping the missing piece, no data repair needed |
